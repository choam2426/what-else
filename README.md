# what-else

> "What else needs to change?" (이 변경으로 또 뭘 바꿔야 하지?)

코딩 에이전트가 **함께 바꿔야 할 곳을 놓치지 않게** 하는 방법을 실험하고 남긴 기록입니다. 그리고 그 기록을 보고 **내 프로젝트에 맞는 형태**를 만드는 안내입니다.

## 왜

에이전트에게 "이거 고쳐 줘"라고 하면 핵심 변경은 잘 하지만, 같이 바꿔야 할 다른 곳을 자주 빠뜨립니다. 릴리스 노트, 다른 백엔드의 같은 코드, 옛 동작에 기대던 호출부 같은 곳입니다. 빠진 곳은 나중에 드러나서 다시 고쳐야 합니다. 코드베이스가 클수록 더 자주 빠집니다.

목표는 **한 번 작업할 때 빠르고, 저렴하고, 정확하게 변경 범위를 모두 찾는 것**입니다.

## 쓰는 법

에이전트에게 이렇게 말하면 됩니다.

```
https://github.com/choam2426/what-else 이거 보고 우리 프로젝트에 맞게 구축해 보자
```

에이전트는 [INSTALL.md](INSTALL.md)를 읽고 이렇게 진행합니다.

1. 프로젝트를 파악하고, git 이력에서 누락이 어디서 나는지 **진단**합니다.
2. 방법 카드를 보고 **추천안과 대안**을 냅니다. "안 함"도 대안에 들어갑니다.
3. 코드를 외부로 보낼지, 비용을 얼마나 쓸지 등을 **사용자와 합의**합니다.
4. 합의한 대로 **만들고**, 그 프로젝트에서 과거에 놓쳤던 변경을 다시 돌려 이번에는 그곳에 닿는지 **검증**합니다.
5. 쓰면서 놓친 곳을 기록해 **계속 고칩니다**.

이 레포에서 프로젝트에 설치되는 것은 없습니다. 만들어진 규칙과 도구는 프로젝트 안에서 혼자 동작합니다.

## 지금까지 알게 된 것

**핵심 결론: 능력이 아니라 과정의 문제였고, 효과를 낸 것은 과정 설계였습니다.**

- 에이전트가 범위를 놓친 것은 찾는 능력이 부족해서가 아니었습니다. 놓친 곳 상당수는 grep 한 번 거리였고, 맥락 없는 서브에이전트가 짚어 줘도 "요청에 없다"며 거절했습니다. 검색 능력을 더 주는 도구(BM25, Jev)는 효과를 더하지 못했습니다.
- 효과를 낸 것은 **에이전트가 어디서 멈추고 어디서 잘못 판단하는지 관찰해서, 그 지점에 단계나 판단 기준을 넣는 것**이었습니다. 끝내기 전에 다시 보는 단계, 맥락 없는 눈으로 보는 단계, "요청에 없으면 범위 밖"이라는 판단을 "깨지는 이유가 맞으면 고친다"로 바꾸는 기준이 그것입니다.
- 프롬프트는 이 설계를 전달하는 수단입니다. 지시를 길고 자세하게 쓰는 것은 효과가 없었고(Django, 범위 찾기 방법론 전체), 짧은 문단이라도 잘못되는 지점에 놓였을 때 효과가 났습니다. 맥락 없는 다른 에이전트처럼 문구만으로는 안 되는 구조도 필요했습니다.

**이렇게 해서 나온 기본 구성은 항상 읽히는 지침에 넣는 두 단계입니다.** 가이드는 모든 구성을 여기서 시작합니다.

1. **끝내기 전에 확인**: 다른 구현, 같은 결정을 내리는 다른 경로, 등록 목록, 호출부, 타입과 스키마를 열어 보고, 요약에 확인한 곳을 적습니다.
2. **다른 눈으로 다시 보기**: 맥락 없는 서브에이전트가 요청과 diff만 보고 빠진 곳을 보고합니다. 작업한 에이전트는 "그대로 두면 무엇이 깨지는지"가 코드로 확인되면, 요청에 이름이 없는 곳이라도 고칩니다.

DeepSWE에서 순정이 반복해서 범위를 놓친 14과제(14개 레포, 5개 언어)를 2회씩 돌린 결과, 범위 누락은 28건 중 순정 15.5, 확인 지시만 11, 두 단계 6이었습니다. 지침 원문은 [방법 카드](guide/methods.md)에 있습니다.

그 밖에 알게 된 것은 이렇습니다.

- **2단계의 "받아들이는 기준"이 핵심입니다.** 기준 없이 다시 보기만 하면 서브에이전트가 빠진 곳을 짚어도, 작업한 에이전트가 "요청에 없다"며 거절해서 확인 지시만 쓴 것과 같았습니다.
- **효과 대부분은 "확인" 단계 자체에서 옵니다.** 레포 규칙, BM25 검색 도구, 둘의 조합도 범위 누락을 약 40% 줄였지만, 도구도 규칙도 없는 확인 지시 한 단락보다 낫지 않았습니다.
- **레포 규칙은 관례 파일 누락에 효과가 있었습니다.** Django에서 처음 보는 변경 12개의 진짜 누락이 7 → 3으로 줄었고, 고친 것은 대부분 릴리스 노트와 레퍼런스 문서였습니다. 두 단계만으로도 이런 누락이 잡히는지는 아직 재지 않았습니다.
- **Jev는 넓은 순위 목록으로는 가장 좋았지만, 에이전트에게 쥐여 주면 잘 쓰지 않았습니다.** 상위 10개에 필수 파일 46/53이 들어 BM25(27), grep(21)보다 나았습니다. 하지만 키와 안내를 주고 쓸지 맡기자 14과제 중 1~3개에서만 썼고, 확인 지시보다 더 줄인 누락은 없었습니다.
- **테스트 통과율로는 범위를 잴 수 없습니다.** DeepSWE 실패는 대부분 구현 오류였고, 범위 누락의 3분의 1 이상은 테스트를 통과한 실행에 숨어 있었습니다. 그래서 범위 누락을 판정자가 직접 판정했고, 판정자에 따른 차이가 커서 같은 판정자가 모든 방법을 함께 보게 했습니다.
- **순정 에이전트가 이미 거의 다 찾는 레포도 있습니다.** SWE-bench Pro의 ansible과 teleport가 그랬습니다. "안 함"도 선택지입니다.
- **작은 모델 워커에게 탐색을 맡기는 구조**는 비용 약 3배, 시간 4~6배가 들었고, 정확도는 레포 규칙만 쓴 것 이하였습니다.

근거는 약함에서 보통 사이이고, 대부분 Claude Code와 Sonnet 계열에서 쟀습니다. 실험이 어떤 순서로 여기까지 왔는지, 조건과 한계, 방법별 모든 비교는 [실험 기록의 "한눈에 보기"](docs/records/README.md#한눈에-보기-2026-10-08-기준)에 있습니다.
