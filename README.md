# what-else

> "What else needs to change?" (이 변경으로 또 뭘 바꿔야 하지?)

코딩 에이전트가 **함께 바꿔야 할 곳을 놓치지 않게** 하는 방법을 실험하고 남긴 기록이에요. 그리고 그 기록을 보고 **내 프로젝트에 맞는 형태**를 만드는 안내예요.

## 왜

에이전트에게 "이거 고쳐 줘"라고 하면 핵심 변경은 잘 하는데, 같이 바꿔야 할 다른 곳을 자주 빠뜨려요. 릴리스 노트, 다른 백엔드의 같은 코드, 옛 동작에 기대던 호출부 같은 곳이에요. 빠진 곳은 나중에 드러나서 다시 고쳐야 해요. 코드베이스가 클수록 더 자주 빠져요.

목표는 **한 번 작업할 때 빠르고, 저렴하고, 정확하게 변경 범위를 모두 찾는 것**이에요.

## 지금까지 알게 된 것

- **정답 구성은 하나가 아니에요.** 같은 방법이 한 레포에서는 누락을 크게 줄이고, 다른 레포에서는 아무것도 바꾸지 않았어요.
- **레포 규칙이 가장 싸고 효과가 컸어요.** "이 레포는 이런 변경 때 무엇을 함께 고친다"를 항상 읽히는 지침에 넣고, "끝내기 전에 확인" 한 줄을 붙였어요.
  - Django에서 처음 보는 변경 12개의 진짜 누락이 7 → 3으로 줄었어요. 작업당 +$0.09, +20초였어요.
  - 고친 누락은 대부분 릴리스 노트, 레퍼런스 문서 같은 관례 파일이었어요.
- **순정 에이전트가 이미 거의 다 찾는 레포도 있어요.** SWE-bench Pro의 ansible과 teleport가 그랬어요.
- **Jev는 넓은 순위 목록으로 쓸 때 좋았어요.** 상위 10개에 필수 파일 46/53이 들어 BM25(27), grep(21)보다 나았어요. 다만 레포 규칙이 있으면 더 보태는 게 없었어요.
- **작은 모델 워커에게 탐색을 맡기는 구조**는 비용 약 3배, 시간 4~6배가 들었고, 정확도는 레포 규칙만 쓴 것 이하였어요.

모두 근거가 약한 편이에요(한 레포, 1회 실행 위주). 조건과 한계는 [실험 기록](docs/records/README.md)에 있어요.

## 쓰는 법

에이전트에게 [`skill/what-else-setup/`](skill/what-else-setup/SKILL.md)을 주고 "이걸 보고 내 레포에 변경 범위 찾기를 세팅해 줘"라고 하세요. 에이전트는 이렇게 진행해요.

1. 레포를 파악하고, 기록에서 누락이 어디서 나는지 **진단**해요.
2. 방법 카드를 보고 **추천안과 대안**을 내요. "안 함"도 대안에 들어가요.
3. 코드를 외부로 보낼지, 비용을 얼마나 쓸지 등을 **사용자와 합의**해요.
4. 합의한 대로 **만들고**, 그 레포의 과거 변경으로 **검증**해요.
5. 쓰면서 놓친 곳을 기록해 **계속 고쳐요**.
