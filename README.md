# what-else

> "What else needs to change?" (이 변경으로 또 뭘 바꿔야 하지?)

코딩 에이전트가 **함께 바꿔야 할 곳을 놓치지 않게** 하는 방법을 실험하고 남긴 기록입니다. 그리고 그 기록을 보고 **내 프로젝트에 맞는 형태**를 만드는 안내입니다.

## 왜

에이전트에게 "이거 고쳐 줘"라고 하면 핵심 변경은 잘 하지만, 같이 바꿔야 할 다른 곳을 자주 빠뜨립니다. 릴리스 노트, 다른 백엔드의 같은 코드, 옛 동작에 기대던 호출부 같은 곳입니다. 빠진 곳은 나중에 드러나서 다시 고쳐야 합니다. 코드베이스가 클수록 더 자주 빠집니다.

목표는 **한 번 작업할 때 빠르고, 저렴하고, 정확하게 변경 범위를 모두 찾는 것**입니다.

## 쓰는 법

에이전트에게 이렇게 말하면 됩니다.

```
https://github.com/choam2426/what-else 이거 보고 우리 프로젝트에 맞게 구축해 보자
```

에이전트는 [INSTALL.md](INSTALL.md)를 읽고 이렇게 진행합니다.

1. 프로젝트를 파악하고, 기록에서 누락이 어디서 나는지 **진단**합니다.
2. 방법 카드를 보고 **추천안과 대안**을 냅니다. "안 함"도 대안에 들어갑니다.
3. 코드를 외부로 보낼지, 비용을 얼마나 쓸지 등을 **사용자와 합의**합니다.
4. 합의한 대로 **만들고**, 그 프로젝트의 과거 변경으로 **검증**합니다.
5. 쓰면서 놓친 곳을 기록해 **계속 고칩니다**.

이 레포에서 프로젝트에 설치되는 것은 없습니다. 만들어진 규칙과 도구는 프로젝트 안에서 혼자 동작합니다.

## 지금까지 알게 된 것

- **정답 구성은 하나가 아닙니다.** 같은 방법이 한 레포에서는 누락을 크게 줄이고, 다른 레포에서는 아무것도 바꾸지 않았습니다.
- **"끝내기 전에 확인" 지시 한 단락이 가장 싸고 효과가 컸습니다.** 다른 구현, 같은 결정을 내리는 다른 경로, 등록 목록, 호출부, 타입과 스키마를 열어 보고 요약에 확인한 곳을 적게 하는 지시입니다.
  - DeepSWE에서 순정이 반복해서 범위를 놓친 14과제(14개 레포, 5개 언어)를 2회씩 돌렸습니다. 범위 누락이 28건 중 16 → 10으로 줄었습니다.
  - 레포 규칙(12.5)과 BM25 검색 도구(10.5)도 함께 판정했는데, 이 지시보다 낫지 않았습니다. 둘을 합쳐도 더 줄지 않았습니다.
- **레포 규칙은 관례 파일 누락에 효과가 있었습니다.** "이 레포는 이런 변경 때 무엇을 함께 고친다"를 항상 읽히는 지침에 넣었습니다.
  - Django에서 처음 보는 변경 12개의 진짜 누락이 7 → 3으로 줄었습니다. 작업당 +$0.09, +20초였습니다.
  - 고친 누락은 대부분 릴리스 노트, 레퍼런스 문서 같은 관례 파일이었습니다.
- **순정 에이전트가 이미 거의 다 찾는 레포도 있습니다.** SWE-bench Pro의 ansible과 teleport가 그랬습니다.
- **Jev는 넓은 순위 목록으로 쓸 때 좋았습니다.** 상위 10개에 필수 파일 46/53이 들어 BM25(27), grep(21)보다 나았습니다. 다만 레포 규칙이 있으면 더 보태는 것이 없었습니다.
- **작은 모델 워커에게 탐색을 맡기는 구조**는 비용 약 3배, 시간 4~6배가 들었고, 정확도는 레포 규칙만 쓴 것 이하였습니다.

근거는 약함에서 보통 사이입니다. 조건과 한계는 [실험 기록](docs/records/README.md)에 있습니다.
