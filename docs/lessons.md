# 해 보면서 배운 것

직접 실험하거나 비슷한 도구를 만드는 사람을 위한 교훈이다. 결과 숫자는 [실험 기록](records/README.md)에 있다.

## 가장 큰 교훈: 능력이 아니라 과정이고, 효과는 과정 설계에서 나온다

에이전트가 함께 바꿔야 할 곳을 놓치는 것은 찾는 능력이 부족해서가 아니었다.

- Django에서 순정이 놓친 곳 상당수는 grep 한 번 거리였다. 찾지 못한 게 아니라 볼 생각을 하지 않았다(R2).
- 검색 능력을 더하는 도구는 효과를 더하지 못했다. BM25 도구는 14과제 모두에서 썼지만 "끝내기 전 확인" 한 단락과 같았고, Jev는 쥐여 줘도 거의 쓰지 않았다(R13~R16).
- 맥락 없는 서브에이전트는 남은 누락을 찾아냈지만, 작업한 에이전트가 "요청에 없다"며 거절했다. 받아들이는 기준을 적자 그제야 반영됐다(R17). 에이전트가 빈틈을 요약에 적고도 고치지 않은 경우도 있었다.

그래서 효과를 낸 것은 모두 과정을 바꾸는 지침이었다. 끝내기 전에 다시 보게 하고, 다른 눈으로 보게 하고, 그 지적을 받아들이게 하는 것이다. 레포 규칙이 Django에서 효과를 낸 것도 이 틀로 설명된다. 규칙은 검색 도구가 아니라, 코드에 없는 관례를 알려 주며 "이 변경이면 여기도 보라"고 주의를 돌리는 지침이다.

이것을 "지시를 명확하게 하라"로 줄이면 맞지 않는다.

- 요청은 원래 명확했다. DeepSWE 요청은 약 2,000자짜리 기능 명세였다.
- 길고 자세한 지시는 효과가 없었다. 범위 찾기 방법론 전체(축 A~G)를 지침에 넣은 Django 실험은 실행 편차 안이었다(R3). 효과를 낸 것은 짧은 문단들이었다.
- 문구만으로는 안 되는 부분이 있었다. 두 번째 검토의 핵심은 "맥락 없는 다른 에이전트"라는 구조였다. 같은 에이전트에게 다시 잘 보라고 해서는 자기 설계 바깥을 보지 못한다.
- 받아들이는 기준은 에이전트가 거절하는 것을 관찰한 뒤에야 쓸 수 있었다.

그래서 효과를 낸 순서는 이렇다. 에이전트가 어디서 멈추는지(보지 않음), 어디서 잘못 판단하는지(보고도 범위 밖으로 돌림) 관찰한다. 그 지점에 단계(다시 보기, 다른 눈으로 보기)나 판단 기준(깨지는 이유가 맞으면 고친다)을 넣는다. 그것을 항상 읽히는 지침에 짧게 쓴다. 프롬프트는 이 설계를 전달하는 수단이다.

새 방법을 만들 때는 "더 잘 찾게 하는가"보다 "에이전트가 어디서 잘못되는지 보았는가, 그 지점에 무엇을 넣는가"를 먼저 묻는다.

## 벤치 설계

- **커밋 메시지를 요청으로 쓰지 않는다.** 너무 짧아서 할 일을 모르거나, 너무 자세해서 정답을 알려준다. 게다가 정답이 커밋 작성자의 구현 하나에 묶인다. 구현 전에 쓰인 요청(이슈, 티켓, PR 설명)을 쓴다.
- **누락은 에이전트 자신의 구현 기준으로 판정한다.** 커밋 메시지 요청에서는 에이전트가 다르게 구현해서 "놓친" 파일의 절반 이상이 실제로는 필요 없었다. 판정자(모델)에게 에이전트의 diff와 원래 diff를 함께 주고, 빠진 파일이 여전히 필요한지 묻게 했다 (`bench/judge-misses.mts`).
- **"범위를 모두 찾아라"라고 시키면 순정에 가장 유리하다.** 실제 사용자는 "이거 해 줘"라고만 한다. 요청을 주고 변경까지 하게 한 뒤 최종 diff로 채점하는 현실형 벤치를 주 벤치로 삼는다.
- **한 번 실행은 편차가 크다.** 같은 순정도 케이스 하나에서 4/4와 2/4가 나오고, 비용은 2~3배 다르다. "순정이 놓친 곳"도 한 번 실행으로 정하면 다른 비교군에 유리하게 기운다.
- **튜닝한 케이스와 판정할 케이스를 나눈다.** holdout은 스펙을 고정한 뒤에만 돌리고, 튜닝 중에는 놓친 내용을 보지 않는다. 규칙도 dev 피드백을 받기 전 버전으로 판정했다.
- **미래가 새지 않게 한다.** 케이스 스냅샷에는 기록을 넣지 않았다. setup은 모든 케이스보다 앞선 시점, 기록을 자른 사본, 원격 없음, GitHub 차단, 도구 호출 감사 조건에서 돌렸다.
- **정답에서 노이즈를 뺀다.** 한 커밋에 섞인 무관한 변경, AUTHORS 같은 파일은 필수/선택 라벨로 거른다. 라벨은 비교군 결과를 모르는 서브에이전트가 diff만 보고 붙였다.
- **seed는 정확한 diff로 만든다.** 공백 무시 diff(`-w`)로 만들면 들여쓰기만 바뀐 줄이 빠져서 문법이 깨진 파일이 생긴다. 적용 후 문법 검사를 한다.

## 범위 누락을 재는 법 (DeepSWE에서 배운 것)

- **테스트 통과율은 범위를 재지 못한다.** DeepSWE 실패는 대부분 구현 오류였고, 범위 누락의 3분의 1 이상은 테스트를 통과한 실행에 숨어 있었다(27회 중 10회). 범위 누락은 테스트와 무관하게 판정자가 직접 판정한다.
- **실패한 과제만 골라 한 번 비교하면 방법의 효과가 부풀려진다.** 한 번 실패한 과제의 40%는 순정을 다시 돌리기만 해도 통과했다. 과제를 고른 뒤 순정을 새로 돌려 그것과 비교한다.
- **판정자 사이의 차이가 방법 사이의 차이보다 크다.** 같은 순정 실행이 판정자에 따라 14개 중 7.5~10.5개 누락으로 판정됐다. 방법은 같은 판정자가 한 과제의 모든 방법 패치를 블라인드로 함께 볼 때만 비교한다(`bench/deepswe-blind-multi.mts`). 판정자는 2명을 두고 일치율을 적는다.
- **일반 판정은 알려진 누락을 놓칠 수 있다.** kea의 연결된 셀렉터는 다섯 방법을 함께 본 판정에서 모두 "누락 없음"이었지만, 그 위치만 짚어 물으니 순정의 누락이 드러났다. 특정 위치가 궁금하면 그 위치만 묻는 집중 판정을 따로 한다.
- **setup은 비교할 때마다 새로 만든다.** 한 번 만든 setup을 재사용하면 그 setup의 운이 방법의 효과로 섞인다. 2회차는 setup부터 다시 했다.
- **방법의 지침 파일은 판정 묶음에서 뺀다.** CLAUDE.md, `.claude/`, 노트 파일이 남으면 판정자가 어느 방법인지 알아챈다.

## 에이전트의 행동 (DeepSWE에서 배운 것)

- **"끝내기 전에 확인" 한 단락이 규칙이나 도구만큼 효과를 냈다.** 레포 규칙과 BM25 도구의 효과 대부분이 함께 붙인 확인 단계에서 왔다. 새 방법은 이 단락만 넣은 조건과 비교한다.
- **쓸 수 있게만 둔 도구는 잘 쓰이지 않는다.** Jev를 키와 문서까지 주고 쓸지는 맡기자 14과제 중 1개에서만 썼다. 에이전트는 후보가 적다고 보면 직접 읽는다. 왜 쓰는지(떠올리지 못한 곳을 찾는 용도)를 적자 3개로 늘었다.
- **다른 눈은 찾고, 작업한 눈은 거절한다.** 맥락 없는 서브에이전트가 남은 누락을 짚었지만, 작업한 에이전트는 "요청에 없다", "호출부가 깨진다"며 거절했다. 받아들이는 기준(깨지는 이유가 코드로 맞으면 요청에 이름이 없어도 고친다)을 적어야 반영됐다.
- **에이전트가 빈틈을 알고도 남겨 두기도 한다.** claude-code-by-agents에서는 요약에 "어떤 provider도 이 도구를 모른다"고 적고 고치지 않았다. 요약에 적힌 빈틈도 검토 대상이다.
- **범위를 넓게 보라는 지시는 요청하지 않은 변경도 늘린다.** 확인 지시를 넣자 요청을 넘어선 변경이 순정의 2.5배가 됐다. 대부분 새 옵션의 문서나 변경 기록처럼 근거가 있는 것이었고, 근거 없는 것은 확인 지시만 대비 비슷했다. 근거 없는 것만 따로 센다.
- **setup은 검증을 자주 건너뛴다.** "검증한다"고 적어도 17개 중 4개만 했다. 검증은 정답이 있는 확인(과거 누락 사건 다시 돌리기)으로 작게 정해 준다.

## 에이전트와 지시문

- **지시는 긍정형으로 쓴다.** "X 하지 마라"보다 "Y 한다"로 쓴다. 부정형은 에이전트가 자주 반복하는 실수나 반드시 막아야 할 부분에만 쓴다. 측정한 결과가 아니라 이 레포의 작성 원칙이다.
- **필수로 시킨 도구 사용은 탐색을 대신해 버린다.** Jev 스캔을 필수로 하자 작은 모델이 직접 찾기를 덜 했고, 필수 파일을 잃었다.
- **skill은 설명(description)으로 불린다.** 실제 요청에 나오는 말("implement", "fix", "rename", "deprecate" 등)로 쓰고, 항상 읽히는 지침에서도 가리켜야 불렸다.
- **harness 동작을 강제로 묶지 않는다.** 특정 서브에이전트만 쓰게 권한을 고정하는 식은 그 harness 전용 구현이 된다. 스펙은 무엇을, 왜만 말하고, 벗어난 사용은 스펙을 고칠 발견으로 다룬다.
- **작은 모델이 쓴 검색 질문은 이미 아는 곳을 확인하는 데 그친다.** "이 파일이 무슨 주제인가" 같은 질문이 나왔다. 넓은 질문(변경 설명 전체)을 넓은 범위에 던지는 편이 순위 도구로는 나았다.
- **작은 모델은 가끔 구조화된 출력 없이 끝난다** (비교군당 약 1/16). 실패로 세고 다시 돌린다.

## Jev

- 요청 하나에 질문을 여러 개 넣을 수 있고, 질문 하나마다 약 17토큰만 더 든다. 같은 조각에 대한 질문은 묶는다.
- 조각 하나만 보고 답하므로, 질문도 조각 하나만으로 답할 수 있어야 한다.
- "변경 전에는 없는 문구"를 물으면 못 찾는다. "추가해야 할 위치인가"를 묻는 질문이 필요하다(예: "다음 릴리스의 릴리스 노트인가").
- 에이전트가 스캔 범위를 정하게 두면 요청이 실행당 수천 건까지 불어날 수 있다. 좁게 먼저, 묶어서 보낸다.

## 환경 (Claude Code, Windows)

- `core.symlinks=false`에서는 심볼릭 링크가 경로 글자만 든 파일로 풀린다. `CLAUDE.md`가 `AGENTS.md`를 가리키는 링크인 레포(outline)는 지침이 로드되지 않았다.
- 이름에 `:`가 든 파일은 Windows에서 만들 수 없다. 스냅샷에서 경고와 함께 건너뛰었다.
- blobless 클론에서 오래된 커밋을 checkout하면 blob을 하나씩 가져와서 몇 시간이 걸린다. 기준 커밋을 `fetch --depth=1`로 받으면 몇 초다.
- `.claude/`는 보호 경로라 dontAsk 모드에서 Write와 Bash 모두 막힌다. setup은 bypass 모드에 차단 목록(홈, GitHub)과 기록 검사를 붙여 돌렸다. bypass에서도 deny 규칙은 적용된다.
- `total_cost_usd`에는 서브에이전트가 포함되지만, `duration_ms`에는 서브에이전트 시간이 빠진다. 시간은 실제 경과 시간으로 잰다.
- `--setting-sources project`로도 사용자 동기화 skill은 로드된다. 비교군을 깨끗하게 하려면 `--disable-slash-commands`를 쓴다.

## 환경 (DeepSWE, Pier, Docker Desktop)

- 전역 `core.autocrlf=true`로 DeepSWE를 받으면 셸 스크립트와 패치가 CRLF가 되어 채점이 깨진다. `git clone -c core.autocrlf=false`로 받는다. Pier 0.3.1도 Windows에서 egress 프록시 파일을 CRLF로 써서 고쳐야 했다.
- Pier를 부른 셸이 시간 제한으로 끊기면 그 뒤 docker.exe가 0xC0000142로 죽어 패치를 잃는다. 배치는 셸과 분리해 띄운다(`bench/deepswe-batch-detached.ps1`). 같은 초에 두 배치를 띄우면 작업 폴더 이름이 겹친다.
- 구독 사용 한도(429)와 이미지 저장소 한도(ECR 429)로 실패한 실행은 모델 실패가 아니다. 따로 옮기고 다시 돌린다. 동시 10개가 이 환경에서 알맞았다(컨테이너당 실제 메모리 1GB 안팎).
- 에이전트 네트워크를 특정 서비스만 열고 싶으면 Pier의 에이전트 허용 도메인을 쓴다(과제는 no-network 그대로). 다만 Claude Code의 WebSearch는 Anthropic 서버에서 실행되어 프록시로 막히지 않으므로 `--disallowedTools`로 끈다.
- 키는 작업 설정 파일에 남는 `--ae` 대신 호스트 환경변수에서 에이전트 프로세스로만 넘긴다. 실행이 끝나면 기록 전체에서 키 문자열을 검색해 0건인지 확인한다.
- setup 에이전트는 환경 문제를 프로젝트 코드로 우회하려 한다(numba setup이 llvmlite 최소 버전 검사를 매번 낮췄다). 방법 변형에는 새 파일과 지침 파일만 넣고 기존 프로젝트 파일 수정은 뺀다.
