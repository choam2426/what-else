## 한 줄 요약

에이전트가 **스펙만 보고 레포에 만든 구현**을 설치했을 때, 순정 harness보다 **한 번의 작업으로 변경 범위를 더 정확하게, 감당할 만한 비용과 시간으로** 찾는지 측정해요.

## 1. 목표와 질문

목표: Agent가 한 번 작업할 때 변경 범위를 빠르고, 저렴하고, 정확하게 모두 찾게 해서, 나중에 빠뜨린 곳을 발견하고 다시 고치는 비용을 줄여요. 코드베이스가 클수록 중요해요.

| # | 질문 | 보는 것 |
| --- | --- | --- |
| Q1 | 더 정확하게 찾는가? | 반드시 바꿔야 할 파일의 재현율, 케이스별로 짝지어 비교 |
| Q2 | 나중에 고칠 일이 줄어드는가? | 케이스마다 놓친 필수 파일 수 |
| Q3 | 비용과 시간은 감당할 만한가? | 환산 비용(메인 + 워커 + Jev), 경과 시간 |
| Q4 | 구현이 스펙대로 움직이는가? | 스펙의 검사 C1~C7 통과율 |
| Q5 | 틀린 후보가 늘어나는가? | 정답이 아닌 파일 수 |

## 2. 비교군

| 비교군 | 설정 | 비고 |
| --- | --- | --- |
| **A. 순정** | Sonnet 5, effort 기본값. 레포에 아무것도 설치하지 않음 | 기준. **이미 측정한 결과를 그대로 써요** |
| **E. 스펙 구현** | Sonnet 5, effort 기본값. 에이전트가 스펙으로 만든 구현(skill, 워커, JevGrep)을 설치 | 본 비교 |

- **두 비교군의 지시문은 바이트 단위로 같아요.** "함께 바뀌어야 할 다른 곳을 모두 찾아라"예요. E에서 skill이 불리는지도 결과에 들어가요(C2).
- **실행 환경은 E만 다르게 둬요.** skill을 켜고, 실행 이벤트를 전부 기록해요. A 레포에는 skill이 없어서 skill을 켜든 끄든 결과가 같아요.
- **A는 다시 돌리지 않아요.** 기존 A 실행(Django dev 2번, dev-2 1번, holdout 1번)을 그대로 써요. 조건을 맞추려고 E를 A와 같은 설정(effort 지정 없음)으로 돌려요. setup은 Sonnet 5 effort medium으로 했지만, setup은 레포마다 한 번이라 비교 조건과 무관해요.
- **나중에 넣을 수 있는 비교군** (이번엔 안 해요)
  - E−Jev: 스펙에서 JevGrep만 뺀 변형으로 setup해서 Jev가 보태는 몫을 봐요.
  - 순정 Haiku: 작은 모델이 혼자 할 때와 비교해요.

## 3. 데이터

| 세트 | 레포 | 케이스 | 쓰임 |
| --- | --- | --- | --- |
| dev | Django 16, pydantic 13 | 29 | 스펙을 다듬고 측정 방법을 확인해요 |
| holdout | pydantic 25 | 25 | 최종 판정에만 써요. 스펙과 구현을 고정한 뒤에 돌려요 |

- **outline은 뺐어요** (2026-09-29). outline의 `CLAUDE.md`는 원래 `AGENTS.md`를 가리키는 심볼릭 링크인데, 이 Windows 환경(`core.symlinks=false`)에서 스냅샷을 만들면 "AGENTS.md"라는 글자만 든 파일이 돼요. 그래서 레포 지침이 A와 E 모두에게 로드되지 않았고, setup이 `AGENTS.md`에 넣은 진입점 안내도 읽히지 않았어요. 스냅샷을 고치면 A도 다시 돌려야 해서 빼기로 했어요. 벤치 결함으로 기록해 둬요.
- pydantic의 심볼릭 링크 2개(`CONTRIBUTING.md`, `tests/pydantic_core`)도 같은 식으로 풀려 있어요. 자동으로 읽히는 파일이 아니고 두 비교군에 같아서 비교에는 영향이 없어요.

- **구현은 레포마다 하나예요.** cutoff 시점 레포에서 setup했어요(Django 2026-07-10, pydantic 06-04, outline 07-28). 모든 케이스 커밋은 cutoff 이후라서 규칙에 정답이 섞이지 않아요.
- **정답은 "반드시 바꿔야 할 파일"이에요.** 커밋 diff만 보고 서브에이전트가 라벨을 붙여요. 비교군 결과는 보지 않아요.
  - dev-2(pydantic, outline): 라벨 있어요.
  - Django dev: 전체 라벨을 새로 붙여요. 지금은 A가 놓친 곳만 라벨이 있어요.
  - holdout: 실행 전에 서브에이전트가 붙이고, 저는 **집계 숫자만** 봐요. 내용을 보면 스펙을 고칠 때 정답이 새요.
- 규모가 클수록 중요하다는 목표에 맞춰 큰 레포(Django, outline)를 주로 봐요. 더 큰 레포를 하나 추가할지는 결정 필요 항목에 넣었어요.

## 4. 실행 방법

1. **설치**: `node bench/run-e2e.mts install <setup-repo> <case-dir>`. setup이 만든 파일을 케이스 스냅샷에 복사하고, 기존 파일을 고친 부분(`CLAUDE.md`, `AGENTS.md`, `.gitignore`)은 패치로 적용해요. 적용에 실패하면 기록해요. JevGrep 캐시와 실행 기록은 git에서 무시하는 파일이라 복사되지 않아요.
2. **실행**
   - E: `run-agent.mts <case> E E-sonnet-<n> --model sonnet` (A와 같은 설정)
   - E는 `TYPESAFE_API_KEY`가 필요하고, 이벤트를 `runs/<run>.events.jsonl`에 남겨요.
3. **반복**: E를 먼저 1번 돌려요. 차이가 편차와 비슷한 크기로 애매하면 그때 E를 한 번 더 돌려요. A의 편차는 Django dev의 A 2번으로 이미 알고 있어요.
4. **채점**
   - 재현율: 필수 라벨 기준. 경로 비교.
   - 비용: `total_cost_usd`(서브에이전트 포함) + Jev 비용. Jev 비용은 구현이 남긴 실행 기록에서 읽고, 없으면 이벤트의 JevGrep 명령 횟수로 추정해요.
   - 적합성: 이벤트에서 뽑아요 (5절).

## 5. 적합성 검사를 이벤트에서 읽는 방법

| 검사 | 이벤트에서 보는 것 |
| --- | --- |
| C2 진입점 사용 | 메인이 `Skill` 도구로 change-scope를 불렀는지 |
| C3 워커에게 위임 | 메인이 `Agent`로 구현이 정의한 워커를 불렀는지, 워커 모델이 haiku인지(`modelUsage`) |
| C4 메인의 읽기 | 메인 모델의 입력 토큰과 메인이 연 파일 수 |
| C5 브리프 형식 | 워커에게 넘긴 프롬프트에 변경, 아는 곳, 볼 곳, JevGrep 질문이 있는지 |
| C6 JevGrep 사용과 재작성 | 워커가 JevGrep 명령을 실행했는지, 같은 대상을 문구를 바꿔 다시 물었는지 |
| C7 보고 형식 | 최종 보고가 위치별 한 줄 형식과 축별 요약을 갖췄는지 |

C1(JevGrep이 실제로 동작)은 setup에서 이미 확인했어요.

## 6. 판정 기준 (holdout, 실행 전에 확정)

제안값이에요. **품질**과 **비용·시간**을 모두 봐요.

1. **품질**: E의 케이스별 평균 필수 재현율이 A보다 **5%p 이상** 높고, 케이스 부트스트랩 95% 구간의 아래쪽이 0보다 커요.
2. **비용**: E의 평균 비용(Jev 포함)이 A의 **1.5배 이하**예요. **시간은 판정에 쓰지 않고 보고만 해요** (2026-09-29 결정). 정확도가 확실히 높으면 4~6배 시간은 받아들일 만하다고 봤어요.
3. **적합성**: C2(진입점 사용)와 C3(워커 위임)이 실행의 **80% 이상**에서 통과해요. 통과하지 못하면 결과가 스펙 때문인지 우연인지 해석할 수 없어요.

- 1~3을 모두 넘으면 **진행**이에요.
- 품질이 같고(차이 ±3%p 안) 비용이 A의 60% 이하면 **"같은 정확도를 더 싸게"**로 따로 기록해요.
- 못 넘으면 원인을 적합성 결과로 나눠 봐요. 스펙 문제인지, 구현 문제인지, Jev의 한계인지 구분해요.

## 7. 순서

1. **스모크**: 레포마다 1케이스(3개)에 설치하고 E를 1번씩 돌려요. 설치, 이벤트 기록, 적합성 추출이 되는지 봐요.
2. **라벨**: Django dev 전체 라벨, holdout 라벨(집계만 봄).
3. **dev 측정**: 29케이스 × E 1번 = 29회. A는 기존 결과.
   - 적합성이 무너지면 스펙을 고치고(v0.3), setup을 다시 해요.
   - 고친 뒤에는 dev를 다시 측정해요.
4. **고정**: 스펙 버전과 구현을 고정해요. 이후로는 바꾸지 않아요.
5. **holdout 판정**: 25케이스 × E 1번 = 25회. 애매하면 E를 한 번 더.

## 11. 현실형 벤치 (2026-09-29 추가)

위 벤치는 "함께 바뀌어야 할 곳을 모두 찾아라"라고 시켜요. 순정 에이전트에게 범위 찾기만 하라는 거라 순정에 가장 유리한 조건이에요. 실제 사용자는 "이거 해 줘"라고 맡기고, 빠진 곳은 나중에 드러나요. 그래서 일반적인 Claude Code, Codex 사용 패턴에 맞춘 벤치를 **주 벤치**로 삼아요. 범위 찾기 벤치는 보조 지표로 남겨요.

| 항목 | 설계 |
| --- | --- |
| 지시 | 커밋 메시지를 요청처럼 줘요(파일 경로 제거). 범위를 찾으라는 말은 없어요 |
| 시작 상태 | 부모 커밋 그대로. seed를 적용하지 않고 에이전트가 핵심 변경부터 해요 |
| E | 같은 시작 상태에 setup으로 만든 구현을 설치하고 커밋해 둬요. 구현 파일이 에이전트의 변경으로 잡히지 않아요 |
| 권한 | 파일 수정, 셸(테스트 포함) 허용. 웹은 막아요(JevGrep은 셸로 Jev에 접속) |
| 모델 | Sonnet 5, effort 기본값. A와 E 같음 |
| 측정 | 최종 diff가 필수 파일을 얼마나 덮었는지(파일 단위), 놓친 필수 파일 수, 불필요하게 건드린 파일 수, 비용, 시간, 진입점 사용(C2) |
| 정답 | 필수 라벨 + seed 파일(핵심 변경이라 필수). 테스트 통과는 보지 않아요 |
| 격리 | 실행마다 스냅샷을 새로 복제해서 작업해요 |

- 도구: `bench/make-real-case.mts`(케이스), `bench/run-task.mts`(실행과 diff 수집)
- 라벨: Django dev 87개 중 필수 72, 선택 15 (`labels-django.json`). pydantic dev-2는 `dev2/labels-pydantic.json`.
- 규모: dev 29케이스 × A, E × 1번. 1회 $1~2 예상.
- **Jev 비용**: 구현이 남긴 JevGrep 실행 기록(요청 수, 입력 토큰)을 `runs/<run>.claude-logs.json`으로 보관해요. 토큰이 기록돼 있으면 $0.042/M으로, 요청 수만 있으면 요청당 평균 토큰으로 환산해서 E 비용에 더해요.
- **배치로 돌려요.** 3~4케이스씩 돌리고 결과, 비용, Jev 요청 수를 확인한 뒤 다음 배치로 가요.
- **E−Jev (Jev 기여 분리)**: 같은 구현을 `TYPESAFE_API_KEY` 없이 돌려요. 구현은 JevGrep을 못 쓴다고 알리고 검색으로 대신해요. E와 짝지어 비교하면 Jev가 보태는 몫이 보여요. 스캔을 생략하는 것 자체는 괜찮아요(Jev 없이 범위를 다 찾으면 그게 더 빠르고 싸요).
- **holdout 전에 구현을 고정해요.** 스펙의 개선 루프(쓰면서 규칙과 구현을 고치는 것)는 dev에서만 돌려요. holdout을 돌리는 동안에는 구현을 바꾸지 않아요. holdout 결과로 고치면 판정에 쓴 정답이 구현에 스며들어요.
- 나중에: Codex에서 같은 스펙으로 setup하고 같은 벤치를 돌려 harness와 무관한지 봐요.

### 12.2 e2e(스펙 → setup → 측정)에서 확인한 것

- setup은 스펙만 보고 3개 레포(Django, pydantic, outline)와 SWE-bench Pro 3개 레포(ansible, teleport, webclients)에서 구현을 만들었어요. 새 레포는 v0.7로 1~2턴, $0.75~1.56.

### 12.3 Jev의 기여

| 실험 | 결과 |
| --- | --- |
| E vs E−Jev (같은 구현, 키만 뺌), Django·pydantic·teleport 12쌍+ | 11쌍 동일, 1쌍은 Jev 쪽이 나쁨. Jev가 찾은 곳은 검색도 찾았음 |
| 독립 평가(서브에이전트, 결론 모르게) | 좁은 범위·구체 질문은 효과 없음. **넓은 범위에 변경 설명 전체를 넣은 일반 질문으로 파일 순위**를 매기면 상위 10에 필수 파일 46/53(BM25 27, grep 21). 순정이 놓친 16개 중 12개가 상위 10. 정밀도 약 28%라 순위로만 쓸 수 있음. 산출물 `jevgrep-bench/eval-jev/` |
| 통제 실험(첫 수정 적용 후 "마무리해 줘"), 10케이스 | A 35/50(70%) → **Jev 상위 15 목록 추가 40/50(80%)**, 비용·시간 동일 |
| 현실형, 규칙 체크리스트(C) vs 체크리스트 + Jev 목록(J), 10케이스 | 진짜 누락 C 5, J 6. 규칙이 있으면 목록이 보태는 것 없음 |

결론: Jev는 **규칙이 없을 때 넓은 순위 목록**으로는 도움이 되지만, 레포 규칙이 있으면 보태는 게 없었어요. 좁게·구체적으로 쓰는 방식(스펙 v0.4~0.7)은 Jev의 강점(넓고 싸게 순위 매기기)을 막았어요.

### 12.4 레포 규칙 체크리스트(C)의 효과

C = setup이 만든 레포 규칙을 `CLAUDE.md`에 넣고 "끝내기 전에 규칙이 가리키는 곳을 확인" 한 줄. 워커·skill·Jev 없음.

"진짜 누락"은 판정자(Sonnet, `bench/judge-misses.mts`)가 에이전트의 **자기 구현 기준으로** 여전히 필요한 파일인지 본 결과예요. 커밋 메시지 요청에서는 에이전트가 다르게 구현해 "놓친" 파일의 절반 이상이 사실 필요 없었어요.

| 실험 | A 진짜 누락 | C 진짜 누락 | 누락 없는 케이스 A → C | 비용 A → C |
| --- | --- | --- | --- | --- |
| dev 10케이스 (커밋 메시지 요청, 규칙은 dev 피드백 반영본) | 20 | 5 | 3 → 7 / 10 | $0.19 → $0.28 |
| **Django holdout 12케이스 (Trac 티켓 요청, v0.1 규칙)** | **7** | **3** | **6 → 10 / 12** | $0.09 → $0.18 (+20초) |
| SWE-bench Pro 7과제 (ansible, teleport; 이슈 설명 요청) | 2 | 2 | 5 → 5 / 7 | $0.24 → $0.29 |

- Django holdout은 가장 깨끗한 조건이에요: 처음 보는 커밋, dev 피드백 전 규칙(v0.1), 구현 전에 쓰인 요청.
- 순정이 놓치는 진짜 누락은 대부분 **레포 관례 파일**(릴리스 노트, 패치 릴리스 노트, 레퍼런스 문서)이고, 규칙이 그걸 채워요. 관례가 약하거나 순정이 이미 거의 다 찾는 레포(teleport)에서는 효과가 없어요.
- 케이스별로는 C 우세 4, A 우세 1 (12케이스 1회씩). 아직 통계적으로 확정은 아니에요.

### 12.5 벤치에 대해 배운 것

- **커밋 메시지를 요청으로 쓰면 안 돼요.** 너무 짧거나(정보 부족) 너무 자세하고(정답 노출), 정답이 커밋 작성자의 구현 하나에 묶여요. 대신 구현 전에 쓰인 요청(Trac 티켓, 이슈)을 쓰고, 누락은 판정자로 보정해요.
- 한 번 실행은 편차가 커요. 같은 순정도 케이스마다 결과·비용이 2~3배 달라요.
- 워커 구조(E)는 비용 약 3배, 시간 4~6배였고 정확도 이득은 C와 비슷하거나 작았어요.
