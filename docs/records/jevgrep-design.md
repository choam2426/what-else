## 한 줄 요약

JevGrep은 코딩 에이전트가 **변경 범위를 빠짐없이 찾도록 돕는 도구**예요. 중요한 변경을 할 때 Jev(TypeSafe AI의 판정 전용 모델)로 레포 전체를 싸게 훑어서 "함께 고쳐야 할 곳"의 후보를 찾아요.

- **배포물은 setup skill이에요.** 에이전트가 레포를 보고 JevGrep을 그 레포에 맞게 설정하게 해요.
- **결과물은 레포 전용 skill이에요.** 쓸 때마다 결과를 기록하고, 쌓인 기록으로 계속 개선돼요.
- **특정 harness에 묶이지 않아요.** Claude Code, Codex, 그 밖의 에이전트 어디서든 써요.
- **만들기 전에 먼저 증명해요.** 순정 harness보다 더 잘, 더 효율적으로 찾는지 Phase 0 실험으로 확인한 뒤에 skill을 만들어요.

## 1. 문제와 기대치

**풀려는 문제는 "에이전트가 함께 고쳐야 할 곳을 놓치는 것"이에요.** grep의 한계는 그 이유 중 하나일 뿐이에요.

- 순정 Claude Code(Sonnet)에 Django 커밋 16개의 변경 범위를 찾게 했더니, **6개 케이스에서 반드시 고쳐야 할 파일을 놓쳤어요** ([phase0-experiment.md](phase0-experiment.md) 12절).
- 놓친 곳 중에는 grep 한 번이면 나오는 곳도 있었어요. 도구가 없어서가 아니라 **그쪽을 찾아볼 생각을 안 해서** 놓쳤어요. 같은 패턴, 같은 역할의 형제, 같은 로직의 다른 경로, 동작이 바뀐 함수의 호출부, 레포 관례상 함께 쓰는 문서가 그랬어요.
- 그래서 JevGrep은 두 가지를 줘요. **어디를 찾아봐야 하는지(방법론, 레포 맞춤 규칙)** 와 **넓게 싸게 확인하는 수단(Jev)** 이에요. 둘의 효과는 Phase 0에서 A'(방법론만)와 B(방법론 + Jev)로 나눠 측정해요.
- 임베딩 RAG는 "비슷한 코드"를 찾지만, "고쳐야 할 코드"는 서로 비슷하게 생기지 않은 경우가 많아요. (가설)

에이전트가 놓치기 쉬운 것 중에서 **Jev에게 현실적으로 기대할 수 있는 것**과 **Jev에게도 어려운 것**을 구분해요. Jev는 판정할 단위 안의 정보만 보고 한 단계로 판단할 때 강하고, 간접 추론에는 약해요.

| 기대할 수 있음 (한 단계 판정) | Jev에게도 어려움 (단위 밖 정보 필요) |
| --- | --- |
| 코드 밖 파일 (migration, 스펙, 설정, i18n, 문서) | 문자열로 조합된 이름 (`f"get_{field}"`, reflection) |
| 테스트와 fixture | 같은 로직을 다른 이름으로 중복 구현한 곳 |
| 스키마, serializer, 타입 선언 | 암묵적인 계약에 기대는 호출부 |

Phase 0에서 종류별로 따로 측정해요.

## 2. 전체 구조

```
JevGrep setup skill (배포물, 레포마다 한 번, 사용자가 직접 호출)
  │  인터뷰 → 탐색 → 설정 결정 → 검증 → 산출물 생성
  ▼
레포 전용 JevGrep (산출물)
  ├─ .jevgrep/          핵심: CLI, 설정, 대상 템플릿, 케이스, 학습 기록 (harness 무관)
  └─ 어댑터             harness마다 얇은 진입점 SKILL.md (+ 가능하면 스캔 워커 정의)
  │
  └─ 쓸 때마다 케이스를 기록하고, 쌓인 케이스로 개선 (9절)
```

### 핵심 CLI 하나를 설정으로 맞춰요

- 레포마다 코드를 고친 복사본을 만들지 않아요. 복사본은 Jev API가 바뀌어도 수정을 받을 수 없고, 레포마다 검증되지 않은 코드가 돼요.
- 대신 **검증된 CLI 하나를 `.jevgrep/config.json`으로 레포에 맞춰요.** 설정으로 안 되는 것만 코드를 고쳐요(탈출구). 고쳤으면 이유를 `learnings.md`에 남겨요.

| CLI 명령 | 역할 |
| --- | --- |
| `scan` | 스캔 실행, run 디렉터리 생성 |
| `record` | 스캔 워커의 판정을 검증해서 run에 기록 |
| `retro` | 작업 완료 후 회고: 스캔 결과와 실제 변경을 비교해 케이스 생성 |
| `runs` | 끝나지 않은 run 목록 |
| `eval` | 케이스 전체로 성능 측정 |
| `doctor` | 키, 네트워크, Node 버전, 어댑터 불일치 점검 |

레포에 맞춰 설정하는 것들이에요.

- 탐색 단위와 크기, 제외 경로, 대상별 후보 수(k), 동시 실행 수
- 대상 템플릿 (레포에서 자주 나오는 "찾을 대상" 유형)
- 사전 필터 조합
- 속도 제한 (사용자의 요금제 한도)

### harness 중립

| 구분 | 내용 | 위치 |
| --- | --- | --- |
| 핵심 (harness 무관, 커밋) | CLI, 설정, 대상 템플릿, 케이스, 학습 기록, 스캔 워커 지시서 | `.jevgrep/` |
| 스캔 기록 (커밋 안 함) | 스캔 한 번마다의 입력, 결과, 판정, 상태 | `.jevgrep/runs/<id>/` |
| 어댑터 (harness별, 커밋) | 그 harness가 skill을 찾는 위치의 진입점, 스캔 워커 정의 | 아래 표 |

| harness | 진입점 | 스캔 워커 | 이어서 부르기 |
| --- | --- | --- | --- |
| Claude Code | `.claude/skills/jevgrep/SKILL.md` | `.claude/agents/jevgrep-scanner.md` | 가능 (`SendMessage`) |
| Codex | `.agents/skills/jevgrep/SKILL.md` (+ 필요하면 `agents/openai.yaml`) | 확인 필요 | 확인 필요 |
| 서브에이전트가 없는 harness | 그 harness의 skill 위치 또는 `AGENTS.md` 한 줄 | 메인이 직접 | 해당 없음 |

원칙:

- **핵심은 한 곳에만 있어요.** 팀원마다 다른 harness를 써도 케이스와 학습 기록이 한 곳에 쌓여야 개선 루프가 돌아가요.
- **진입점은 같은 템플릿에서 생성해요.** 표준 frontmatter(`name`, `description`)만 쓰고, 레포 루트 기준 경로로 `.jevgrep/`를 가리켜요. `${CLAUDE_SKILL_DIR}`, 동적 컨텍스트 주입 같은 harness 전용 기능에 기대지 않아요. 템플릿 버전을 적어두고 `doctor`가 불일치를 찾아요.
- **안전장치는 CLI 안에 둬요.** 도구 제한이나 작은 모델은 일부 harness에만 있어요. 제외 경로, 비밀정보 필터, 후보 수 상한은 CLI가 지켜요.
- **샌드박스 차이를 안내해요.** 네트워크를 막거나 환경 변수를 넘기지 않는 harness가 있어요(예: Codex 기본 샌드박스). 어댑터에 api.typesafe.ai 접근 허용과 키 전달 방법을 적어요.
- **모델은 등급으로 적어요.** 스캔 워커는 "작은 모델"로 적고, 어댑터가 harness별 모델 이름으로 바꿔요.
- **setup이 harness를 알아내요.** 인터뷰에서 팀이 쓰는 harness를 묻고, `.claude/`, `.agents/`, `AGENTS.md` 같은 흔적도 확인해서, 쓰는 harness의 어댑터만 만들어요.

### 기술 선택

- TypeScript `.mts`로 작성해요. 복사해 간 레포의 `package.json`이 `"type": "commonjs"`여도 항상 ES 모듈로 실행돼요.
- 타입만 지우면 실행되는 문법(`erasableSyntaxOnly`)만 써요. Node 22.18 이상에서는 그대로 실행되고, 그보다 낮은 환경을 위해 번들한 단일 `.mjs`도 같이 배포해요.
- 외부 패키지를 쓰지 않아요. Jev 호출은 Node 내장 `fetch`로 해요 (엔드포인트가 `POST /v1/systemone` 하나뿐).
- 더 엄격한 tsconfig(`exactOptionalPropertyTypes`, `noPropertyAccessFromIndexSignature`)에서도 타입 검사를 통과하도록 이 저장소에서 그 옵션을 켜고 검사해요.
- API 키는 공식 SDK와 같은 환경 변수 `TYPESAFE_API_KEY`에서 읽어요. 엔드포인트는 `TYPESAFE_BASE_URL`로 바꿀 수 있어요. 생성되는 파일에는 키를 절대 쓰지 않아요.

## 3. 핵심 원칙: 추론은 LLM, 인식은 Jev

Jev는 간접 추론에 약해요. 그래서 **"무엇이 바뀌는지"와 "무엇을 찾는지"를 분리**해요.

```
변경:  User.email becomes required (non-null)
        │  메인 에이전트(LLM)가 "영향받는 코드의 종류"로 분해
        ▼
찾을 대상:
  T1. User를 email 없이 생성하는 코드
  T2. email이 None일 때를 처리하는 분기
  T3. email을 optional로 선언한 타입·스키마·serializer
  T4. email 없는 User를 만드는 테스트·fixture
        │  Jev가 각 코드 조각이 어떤 대상에 해당하는지 판정
        ▼
후보 목록 (걸린 대상 = 이유)
```

- 추론은 메인 에이전트가 하고, Jev는 "이 코드가 이런 종류인가?"라는 한 단계짜리 판정만 해요.
- grep에 글자 패턴을 주듯, JevGrep에는 **의미 패턴**을 줘요.
- 걸린 대상이 곧 후보의 이유가 돼요. Jev가 설명을 생성하지 못하는 한계를 보완해요.
- 한계: 에이전트가 분해하면서 떠올리지 못한 종류는 찾지 못해요. 그래서 대상 템플릿과 개선 루프가 중요해요.

## 4. 입력 설계

입력은 **변경 맥락 1개 + 찾을 대상 N개**예요. Jev 문서의 원칙대로 state에는 내용과 사실을, question에는 판정을 넣어요.

```json
{
  "state": {
    "context": "User.email becomes required (non-null). Before: `email: Optional[str] = None`, after: `email: str`.",
    "unit": {
      "path": "api/serializers/user.py",
      "language": "python",
      "code": "L001| def validate(self, attrs):\nL002|     ..."
    }
  },
  "questions": {
    "T1": {
      "type": "noul",
      "instructions": "Does this code create a User without providing an email?",
      "criteria": {
        "true": "Constructs or saves a User where email is omitted, None, or may be missing",
        "false": "Always passes an email, or does not create Users"
      }
    },
    "T2": { "type": "noul", "instructions": "..." },
    "line": { "type": "choice", "instructions": "Which line most needs to change?", "criteria": { "L001": null, "L002": null } }
  }
}
```

### state

- `context`: 메인 에이전트가 써요. 요약 문장만 쓰지 말고 **before/after 코드 조각**을 넣어요.
- 모든 문장은 영어로 써요. Jev는 비영어권 언어에서 정확도가 떨어져요.
- 줄 ID는 위치를 찾아야 할 때만 붙여요. choice 선택지가 최대 255개라서, 그보다 긴 단위에는 못 붙여요.
- 컨텍스트 한도: 약 2만 토큰은 성공, 약 5만 토큰 이상은 `max_tokens_exceeded`로 실패했어요. 문서상 한도(state + 가장 긴 질문 32k)는 정확히 확인하지 못했어요.

### 질문

| 질문 | 타입 | 역할 |
| --- | --- | --- |
| `T1`…`Tn` | noul | 찾을 대상별 판정 |
| `line` | choice | 가장 먼저 고칠 줄 (semantic find 패턴) |

- 같은 요청 안의 질문은 병렬로 평가돼서, 질문을 늘려도 응답 시간이 거의 늘지 않아요. state는 요청당 한 번만 과금돼요.
- 질문끼리는 서로의 답을 참조할 수 없어요.

v1에서 **빼는** 질문이에요. Phase 0에서 도움이 확인되면 넣어요.

- **포괄 질문 `T_any`** ("이 변경 후에 이 코드가 틀리게 되나?"): Jev가 약한 간접 추론 질문 그 자체라서 오탐의 주범이 될 가능성이 높아요.
- **반대 문구 질문 `Tn_neg`**: 문구 민감성을 줄이려는 아이디어지만, 논리가 복잡해지고 질문 수가 두 배가 돼요. 넣더라도 recall이 우선이라 평균이 아니라 최댓값으로 합쳐요.

### 찾을 대상 작성법

진입점 `SKILL.md`의 핵심 섹션이 돼요.

- 단어 언급이 아니라 **코드가 하는 일**로 써요. ("email을 언급하는 코드" 대신 "email 없이 User를 생성하는 코드")
- false 기준에 흔한 오탐을 넣어요. ("email을 화면에 표시만 함")
- 코드 밖 대상도 떠올려요. (migration, 설정, 문서, i18n, CI 스크립트)
- 피할 질문: 개수 세기, 날짜 비교, 산수, state 밖의 정보가 필요한 질문("이 함수를 호출하는 곳이 바뀌었나?")
- 레포에서 자주 나오는 대상 유형은 **대상 템플릿**(`.jevgrep/targets/`)으로 만들어둬요.

## 5. 탐색 설계

### 탐색 단위

| 단위 | 장점 | 단점 | v1 |
| --- | --- | --- | --- |
| **줄 창 (약 60줄, 겹침)** | 언어 무관, 파서 불필요 | 함수 중간이 잘림 | **기본값** |
| 파일 | 요청 수 적음, 맥락 보존 | 큰 파일은 정확도 하락, 255줄 넘으면 줄 위치를 못 짚음 | 짧은 파일, 설정 파일에만 |
| 함수·심볼 | 판정 대상이 선명함 (가설) | 언어별 파서 필요, 맥락 잘림 | 미룸 |
| 계층형 (파일 요약 → 함수 → 줄) | 요청 수 크게 감소 | 첫 단계가 요약만 보고 판정하는 간접 추론이라, 놓치면 복구 불가 | 미룸 |

- **여러 단위를 한 요청에 묶기**는 미뤄요. 요청 수는 줄지만, 각 질문 입장에서는 나머지 단위가 무관한 내용이라 정확도가 떨어질 수 있어요. 요청당 최대 질문 수(10개까지만 확인됨)도 제약이에요.

### 후보 선정 (레포 맞춤의 핵심)

**전체 스캔은 기본값이 아니에요.** 1회 테스트(2026-09-28)에서 Django 전체 15,673개 단위를 스캔하는 데 약 13분이 걸렸어요. 요청 한도(초당 20개)에 묶여 있어서예요. 같은 케이스에서 순정 Claude Code는 193초에 끝났어요. 그래서 후보를 먼저 추리고, **시간 예산** 안에서만 Jev로 판정해요. 예를 들어 60초면 약 1,200개 단위예요. 전체 스캔은 깊게 볼 때만 선택하는 옵션(`--all`)으로 둬요.

후보 선정의 중심은 **레포 맞춤 규칙**이에요. 단어 기반 검색(BM25 등)은 여러 출처 중 하나일 뿐이에요. 단어 기반 선정에 기대면 grep이 놓치는 곳을 똑같이 놓칠 수 있어요.

| 후보 출처 | 무엇을 잡나 | 비용 |
| --- | --- | --- |
| **레포 맞춤 규칙** (변경 종류 → 함께 바뀌는 경로) | 예: DB 버전 변경이면 `docs/ref/databases.txt`, `docs/releases/`, `.github/workflows/` | 로컬. setup과 개선 루프에서 쌓임 |
| 대상별 경로 범위 | 예: 릴리스 노트 대상은 `docs/releases/`만, CI 대상은 `.github/`만 | 로컬 |
| git co-change | 과거에 seed 파일과 같이 바뀐 파일. 문서, 설정, 테스트처럼 코드 참조가 없는 짝 (가설) | `git log` |
| seed 주변 | seed 파일 자체, 같은 디렉터리 | 0 |
| 단어 기반 검색 (BM25 등) | 단어가 겹치는 곳. 대상 문장이 풍부하면 grep보다는 넓게 잡혀요 | 로컬 |
| import·호출 그래프 | 코드 참조로 이어진 곳. 동적 참조는 놓침 | 파서 필요. 미룸 |

**여기가 레포 맞춤이 효과를 내는 곳이에요.** 범용 도구는 어느 레포에나 같은 선정 규칙을 써요. 우리는 setup과 개선 루프에서 레포 지식을 쌓아요.

- 변경 종류별로 함께 바뀌는 위치 (예: Django의 DB 버전 변경 → `docs/ref/databases.txt`, `docs/releases/`, `.github/workflows/`)
- co-change 관계, 레포 용어, 레포 관례(예: 기능 변경에는 릴리스 노트)
- 놓침이 나오면 "이런 변경이면 이 경로도 본다"는 규칙이 하나씩 늘어나요.

이 지식은 `.jevgrep/config.json`과 `.jevgrep/targets/`에 쌓여요.

### 비용과 시간

30만 줄 레포 전체 스캔 기준이에요. 자세한 계산은 [리서치 노트](../research/jev.md) 6~7절에 있어요.

- 비용: 약 $0.19 (실측 코드 토큰 밀도 기준). 사실상 무시할 수준이에요.
- 요청마다 약 270 tokens의 고정 오버헤드가 붙어요.
- 시간: 병목은 비용이 아니라 요청 한도(분당 1,200회)예요. 60줄 창이면 요청이 수천 개라 수 분이 걸릴 수 있어요. Phase 0에서 실측해요.
- 평가를 반복하면 요청 수가 크게 늘어요. 단위별 결과를 내용 해시로 캐싱해요.

## 6. 출력 설계

에이전트 컨텍스트가 가장 비싼 자원이라, 요약만 출력하고 전체 결과는 run 디렉터리에 남겨요.

```
jevgrep scan --query query.json [--grep-hits hits.txt]

run 20260928-1432-a7f3 · scanned 4,812 units in 412 files (3m12s) · excluded 3 paths · failed 0 · complete

T1  User를 email 없이 생성 (top 10)
  0.94  api/serializers/user.py:40-99          new
  0.81  api/views/signup.py:120-179            hit
  ...
T3  email을 optional로 선언 (top 10)
  0.91  api/schemas/user.py:1-60               new
  ...
full results: .jevgrep/runs/20260928-1432-a7f3/results.json
```

- **자르는 기준은 절대 점수가 아니라 대상별 상위 k개예요.** 대상 문구는 작업마다 새로 쓰고 Jev는 문구에 민감해서, 0.7 같은 절대 점수 기준은 작업 사이에 통하지 않아요. 조정하는 것도 점수가 아니라 k예요.
- **오탐이 많을 수 있어요.** 레포 규모에서는 진짜가 드물어요. 1,500개 단위 중 진짜 10개라면 오탐률 2%에서도 대상당 약 30개가 오탐이에요. 그래서 상위 k개로 자르고, Phase 0에서 recall과 함께 케이스당 후보 수를 재요.
- `grep` 열(new / hit): 메인이 grep으로 이미 찾은 곳인지 보여줘요. 다만 이 열의 의미는 메인이 넘긴 grep 결과만큼만 믿을 수 있어요.
- **coverage를 항상 보고해요.** 실패율이 기준을 넘으면 `incomplete`로 표시하고, 스캔하지 못한 경로를 grep 대상으로 알려줘요. 숨기면 에이전트가 "없다"를 "확인했다"로 착각해요.

## 7. 사용 흐름 (레포 전용 skill)

### 트리거

- 에이전트의 자기 판단("grep으로 확신할 수 없으면")에만 기대지 않아요. 이 도구가 필요한 건 에이전트가 **잘못 확신할 때**니까요.
- **객관적인 변경 종류**로 트리거해요. 스키마·API 계약, 설정 키, enum 값, feature flag, 권한 변경 같은 것들이에요.
- 트리거하면 안 되는 경우도 분명히 적어요. 단순 이름 변경, 한 파일 안의 수정처럼 grep 패턴 하나로 범위가 확실한 경우예요.
- description은 비슷하지만 다른 요청(near-miss)으로 harness마다 평가해요.

### 비용 단계: Jev → 스캔 워커 → 메인

```
Jev          : 레포 전체 수천 단위를 판정       (가장 쌈, 판정만 함)
  ▼ 대상별 상위 k개
스캔 워커     : 후보 코드를 직접 읽고 검증       (작은 모델, 읽기 위주)
  ▼ 검증된 목록 + 스캔 회고
메인          : 실제 수정                      (가장 비쌈, 판단이 필요한 일만)
```

- 단계마다 더 비싼 모델이 더 적은 양을 처리해요. 후보를 하나하나 읽는 일을 스캔 워커가 가져가서, 메인은 짧은 보고만 받아요.
- **스캔 워커는 역할 이름이에요.** 서브에이전트가 있으면 작은 모델 서브에이전트가, 없으면 메인이 맡아요. 어느 쪽이든 `.jevgrep/worker.md`를 따라요.
- **v1에 스캔 워커를 넣을지는 Phase 0 결과로 정해요.** "이 후보를 정말 고쳐야 하나"를 판단하는 것도 간접 추론이라, 작은 모델이 진짜 후보를 버릴 위험이 있어요. 넣지 않으면 v1에서는 메인이 CLI 출력을 직접 읽어요.

### 역할 분담

| 단계 | 담당 | 이유 |
| --- | --- | --- |
| 변경 맥락과 찾을 대상 작성 | **메인** | 결과 품질을 가장 좌우하는 추론 단계이고, 변경을 제일 잘 이해하는 것도 메인이에요 |
| 스캔 실행, 후보 읽기, 검증 | 스캔 워커 | 읽기 위주의 반복 작업이에요 |
| 후속 변경 탐색 | 스캔 워커는 **보고만** | 새 계약 변경을 알아채는 건 추론이 필요해요. 메인이 판단해서 다시 맡겨요 |
| 수정 | **메인** | |
| 스캔 직후 회고 | 스캔 워커 | 방금 후보를 읽었으니 스캔 품질을 가장 잘 알아요 |
| 작업 완료 후 회고 | `jevgrep retro` (스크립트) + LLM 주석 | 분류는 스크립트가 정확해요. LLM은 놓친 원인만 적어요 |

### 흐름

1. 평소처럼 grep으로 먼저 찾아요.
2. 트리거 조건에 해당하면 JevGrep을 써요.
3. **메인**이 변경 맥락(before/after 포함)을 쓰고, 찾을 대상 N개로 분해해요. 대상 템플릿을 활용해요.
4. **메인**이 `jevgrep scan`을 실행하거나, 스캔 워커에게 맡겨요. grep 결과도 같이 넘겨요.
5. **스캔 워커**가 후보를 읽고 검증해서, 판정을 `jevgrep record`로 기록하고 보고해요.
6. **메인**이 보고를 보고 수정해요. 후속 변경이 있으면 판단해서 3번으로 돌아가요. 간접 추론을 반복으로 풀어요.
7. 작업이 끝나면 `jevgrep retro`로 회고해요 (9절).

**Jev도 스캔 워커도 못 찾았다고 해서 고칠 곳이 없다는 뜻은 아니에요.** 진입점 `SKILL.md`에 명시해요.

### run 디렉터리

어떤 에이전트든, 어떤 harness든 이것만 읽으면 이어서 일할 수 있는 **인수인계 기록**이에요. **스크립트만** 써요.

```
.jevgrep/runs/<id>/          # id = 시간 + 난수. 동시에 여러 세션이 돌아도 겹치지 않음
  meta.json      # 기준 커밋, 커밋 안 된 변경의 지문, 스캔한 파일의 내용 해시, 설정 버전
  query.json     # 변경 맥락과 찾을 대상 (고정 보관)
  grep-hits.txt  # 메인이 grep으로 이미 찾은 위치
  results.json   # 스캐너 출력 전체 (점수, 위치, coverage)
  verdicts.json  # 스캔 워커의 판정 (record가 검증 후 기록)
  report.md      # 사람이 읽는 보고 (record가 생성)
  status         # scanned → reported → retro-done
```

- 기준 커밋과 내용 해시가 있어서, 최종 diff의 기준점이 분명하고 줄이 밀려도 후보 위치를 맞출 수 있어요.
- 커밋하지 않아요. 대상 레포의 `.gitignore`에는 `.jevgrep/runs/`만 넣어요.

### 스캔 워커 보고 형식

```
## 후보
확실 (3)
  api/serializers/user.py:40-52   T1  0.94  email 없이 User(**data) 생성
  api/schemas/user.py:12-14       T3  0.91  email: Optional[str] 선언
  tests/fixtures/users.py:12-30   T4  0.88  email 없는 fixture 3개
가능성 있음 (2)
  billing/invoice.py:88-95        T2  0.72  user.email을 None 체크 없이 사용, 영향 불확실
  ...
제외 (4)
  admin/views.py:10-22            T2  0.81  email을 표시만 함, 변경 영향 없음
  ...

## 후속 변경 가능성
- UserSerializer.to_representation의 반환 타입도 바뀔 수 있음 (확인 필요)

## 스캔 회고
- 스캔 범위: 4,812 단위 / 실패 0 / 컨텍스트 초과로 분할 2
- 오탐 경향: T2가 "email을 표시만 하는 코드"에 반복적으로 걸림 → T2의 false 기준 보강 제안
- 대상 문제: T5는 아무것도 걸리지 않음 → 질문 문구 점검 필요
```

- 후보를 **버리지 않아요.** 제외한 것도 한 줄 이유와 함께 보여줘서 메인이 뒤집을 수 있게 해요. 작은 모델이 진짜 후보를 조용히 버리는 게 가장 위험해요.
- 형식은 `위치 · 대상 · Jev 점수 · 판정 · 한 줄 이유`로 고정해요. 워커는 이걸 JSON으로 `record`에 넘기고, `report.md`는 스크립트가 만들어요.
- 스캔이 돌지 않았으면(키 없음, 네트워크 막힘) "스캔 안 됨"을 분명히 보고해요. "찾은 것 없음"과 헷갈리면 안 돼요.

### harness별 차이

| 상황 | 스캔 워커 | 작업 완료 후 회고 |
| --- | --- | --- |
| 서브에이전트 + 이어서 부르기 가능 (예: Claude Code) | 작은 모델 서브에이전트 | `retro` 스크립트. 원하면 같은 워커를 이어서 불러 원인 주석을 달게 해요 |
| 서브에이전트는 있지만 이어서 부르기 불가 | 서브에이전트 | `retro` 스크립트 + 새 워커가 run 기록을 읽고 주석 |
| 서브에이전트 없음 | 메인이 직접 | `retro` 스크립트 + 메인이 주석 |

진입점 `SKILL.md`에는 세 경로가 모두 쓰여 있어야 해요. 어느 경로든 run 디렉터리와 케이스 형식은 같아요.

## 8. setup skill 흐름

setup skill은 **사용자가 직접 호출**할 때만 써요. 레포마다 한 번 실행하고, 파일을 만들고, API 비용을 쓰기 때문이에요. Claude Code에서는 `disable-model-invocation: true`로, 그 기능이 없는 harness에서는 description에 "사용자가 명시적으로 요청할 때만"을 써서 막아요.

1. **인터뷰** (사용자에게 묻기)
    - 팀에서 어떤 harness를 쓰나요?
    - 코드를 외부 API(TypeSafe)로 보내도 되나요? 추가로 제외할 경로가 있나요?
    - 이 레포에서 고치다 보면 꼭 빠뜨리는 게 뭔가요? (대상 템플릿의 출발점)
2. **탐색** (에이전트가 확인)
    - 언어 구성, 모노레포 여부, 생성 코드·vendor 디렉터리
    - 파일 간 결합 방식 (스키마, 설정, 문자열 키)
    - 이미 있는 harness 설정 (`.claude/`, `.agents/`, `AGENTS.md`)
    - 쓸 만한 커밋 기록이 있는지
3. **설정 결정**: `config.json`과 초기 대상 템플릿을 정하고, 결정 이유를 `learnings.md`에 남겨요.
4. **검증 (필수 관문)**: 레포의 과거 커밋으로 평가해요. 방법은 Phase 0 프로토콜과 같아요 ([phase0-experiment.md](phase0-experiment.md) 4~6절).
    - 부모 커밋 스냅샷, 핵심 hunk 하나를 seed로, 경로를 지운 커밋 메시지
    - 원래 있던 파일만 정답으로
    - 완료 기준: 커밋 N개로 recall@k를 측정하고, 순정 harness 대비 수치를 사용자에게 보고함
    - 쓸 만한 커밋 기록이 없으면 "평가 불가"로 표시하고, 사용하면서 케이스가 쌓이면 평가해요.
    - **"이 레포에는 설치하지 않음"도 정상적인 결론이에요.**
5. **산출물 생성**: `.jevgrep/`, 쓰는 harness의 어댑터, `.gitignore`의 `.jevgrep/runs/` 한 줄

## 9. 개선 루프

레포 전용 skill은 한 번 만들고 끝나지 않아요. **쓸 때마다 케이스가 기록되고, 쌓인 케이스로 설정과 대상 템플릿이 개선돼요.**

### 신호

작업이 끝나면 "스캔이 뭘 찾았는지"와 "실제로 뭘 고쳤는지"를 비교할 수 있어요.

| 분류 | 의미 | 개선 방향 |
| --- | --- | --- |
| 적중 | 후보였고 실제로 고침 | 유지 |
| 놓침 | 실제로 고쳤는데 후보에 없음 | 새 대상 템플릿, k 조정, 청크 분할 수정, 사전 필터 추가 |
| 오탐 | 상위 후보였는데 고치지 않음 | 대상의 false 기준 보강, 제외 경로 추가 |
| 검증 놓침 | 워커가 "제외"했는데 결국 고침 | 워커 지시서 보강. Jev와 별개로 추적 |

- 가장 가치 있는 신호는 **놓침**이에요. 놓친 코드의 종류가 곧 다음에 추가할 대상 템플릿이 돼요.
- 라벨은 공짜지만 완벽하지 않아요. 에이전트는 스캔이 보여준 곳을 더 많이 고치는 경향이 있고, 에이전트도 Jev도 같이 놓친 곳은 diff에 아예 없어요. 그래서 작업 직후의 diff보다 **리뷰를 거쳐 머지된 커밋**이 더 믿을 만해요. 케이스마다 정답의 출처를 기록해요.

### 회고 두 번

| 시점 | 누가 | 결과물 |
| --- | --- | --- |
| 스캔 직후 | 스캔 워커 | `verdicts.json` + `report.md`의 "스캔 회고" (오탐 경향, 대상 문제, 스캔 범위 문제) |
| 작업 완료 후 | `jevgrep retro` + LLM 주석 | 확정 케이스(`.jevgrep/cases/`) + 패턴이 보이면 `learnings.md` |

- 스캔 직후 회고는 워커가 후보를 읽은 기억이 생생할 때 해야 원인 분석이 정확해요. 그래서 기억에만 두지 않고 바로 기록해요.
- 작업 완료 후 회고는 **스크립트가 주 경로**예요. 분류는 스크립트가 하고, LLM은 놓친 원인에 주석만 달아요.
- 회고를 잊을 수 있어요. 다음 `scan` 때 끝나지 않은 오래된 run을 자동으로 닫고, 나중에 머지된 커밋 기준으로 다시 라벨을 붙여요.

### 구성

```
.jevgrep/                   # 핵심 (harness 무관, 커밋)
  jevgrep.mjs               # 번들된 CLI (scan, record, retro, runs, eval, doctor)
  config.json               # 레포별 설정
  worker.md                 # 스캔 워커 지시서
  targets/                  # 대상 템플릿. 사용하면서 늘어남
  cases/                    # 확정 케이스
    holdout/                # 개선에 쓰지 않는 평가 전용 케이스
  learnings.md              # 원인 분석, 바꾼 것과 그 이유, 전후 수치
  runs/                     # 스캔 기록 (커밋 안 함)

# harness별 어댑터 (쓰는 harness만 생성, 커밋)
.claude/skills/jevgrep/SKILL.md     # Claude Code 진입점
.claude/agents/jevgrep-scanner.md   # Claude Code 스캔 워커 (작은 모델, 읽기 + CLI 실행만)
.agents/skills/jevgrep/SKILL.md     # Codex 진입점
```

- 사용 기록과 원인 분석은 `SKILL.md`가 아니라 `cases/`와 `learnings.md`에 쌓아요. `SKILL.md`가 계속 불어나면 에이전트가 읽기 힘들어져요.

### 두 단계 개선

1. **가벼운 회고 (매번)**: 케이스를 기록하고, 뻔한 원인은 한 줄 적어요.
2. **개선 (가끔)**: 해결하지 않은 놓침이 쌓이면, 원인을 묶어보고 설정과 템플릿을 고쳐요. 이때 **가지치기도** 해요. 해결된 원인, 중복된 템플릿, 낡은 기록을 정리해요. 추가는 쉽고 삭제는 어려워서 가만히 두면 낡은 층이 쌓여요.

### 관문

"recall이 떨어지면 반영 안 함"만으로는 부족해요. k를 늘리면 recall은 항상 올라서 후보를 쏟아내는 방향으로 흘러가고, 케이스가 20개쯤이면 recall 오차가 ±12~20%p라 우연에 좌우돼요.

- **상위 k개 기준 recall**로, 케이스별로 짝지어 비교해요.
- **평가 전용 케이스**(`cases/holdout/`)로 평가해요. 놓침에서 만든 템플릿을 그 놓침으로 평가하면 당연히 좋아 보이니까요.
- 이전에 찾던 진짜를 **하나라도 잃으면** 반영하지 않아요.
- 최소 케이스 수를 숫자로 정해요. (Phase 0 결과를 보고 정해요) 그 전에는 템플릿 추가만 해요.
- 에이전트가 만든 개선은 사용자 작업과 섞이지 않게 **별도 커밋으로 제안**해요. 여러 팀원이 동시에 `cases/`, `learnings.md`를 고쳐 충돌하는 것도 줄어요.
- `SKILL.md`나 `worker.md`처럼 에이전트 행동을 바꾸는 수정은 사용자에게 먼저 제안해요.

## 10. 보안과 실패 처리

### 보안 기본값

- `git ls-files`에 있는 파일만 스캔해요.
- 기본 제외 경로: `.env*`, 키·인증서, 자격 증명 파일, terraform state, 생성 파일, lock 파일
- 전송 전에 비밀정보 패턴을 걸러내요. 과거 커밋에는 지워진 비밀정보가 남아 있을 수 있어서, 평가할 때도 같은 필터를 적용해요.
- 레포 내용이 에이전트에게 들어가면 프롬프트 인젝션 경로가 될 수 있어요. 에이전트가 쓴 `targets/`, `learnings.md`도 이후 컨텍스트에 들어가요. 스캔 워커의 셸 권한은 가능한 harness에서는 CLI 실행으로 제한해요.
- 에이전트가 CLI 코드를 고치는 것(탈출구)은 코드를 다른 곳으로 보내는 통로가 될 수 있어요. 코드 수정은 사용자 확인을 거쳐요.

### 실패 처리

| 상황 | 동작 |
| --- | --- |
| 키 없음, 네트워크 막힘 | "스캔 안 됨"을 분명히 보고하고, 에이전트가 grep으로 대체하게 해요 |
| 일부 요청 실패 | 실패율이 기준을 넘으면 `incomplete`로 표시하고, 스캔 못 한 경로를 grep 대상으로 알려줘요 |
| 컨텍스트 초과 | 단위를 쪼개서 다시 보내요. (현재 `scanUnits`는 감지만 하고 쪼개지 않아요) |
| 쓸 만한 커밋 기록이 없음 | 검증을 "평가 불가"로 표시해요 |
| setup 검증 실패 | 설치하지 않아요 |

## 11. 리스크

- **핵심 전제가 틀릴 수 있어요.** Phase 0에서 "효과 없음"으로 끝날 수 있어요. 그래서 기준을 미리 정해두고 실험부터 해요.
- **코드가 외부 회사로 전송돼요.** TypeSafe의 데이터 보관·학습 사용 정책을 아직 확인하지 못했어요. setup을 돌린 사람 외에 팀원의 동의를 어떻게 받을지도 정해야 해요. 회사 코드에 쓰기 전에 가장 먼저 풀어야 할 문제예요.
- **Jev는 early access예요.** 한도와 가격이 바뀔 수 있고, 문서와 실제 동작이 다른 부분도 있었어요. 벤더에 종속돼요.
- **오탐이 많으면 에이전트 컨텍스트를 낭비해요.** 상위 k개로 자르고, Phase 0에서 후보 수를 재요.
- **개선 루프가 잘못된 방향으로 흐를 수 있어요.** 관문(9절)으로 막아요.

## 12. 검증할 가설

Phase 0에서 확인할 것:

- [ ] 순정 harness에 JevGrep을 붙이면, 순정 harness가 놓친 진짜 위치를 더 찾는다
- [ ] 그 비용(토큰, 시간)이 감당할 만하다
- [ ] 좋아진 게 Jev 덕이다 (Jev 스캔 결과만으로도 의미 있는 recall이 나온다)
- [ ] 도움이 되는 건 한 단계 판정 종류(코드 밖 파일, fixture, 선언부)다
- [ ] 작은 모델 스캔 워커의 검증이 진짜 후보를 거의 버리지 않는다 (확장 단계)

나중에 확인할 것:

- [ ] 대상별 질문이 포괄 질문 `T_any` 하나보다 낫다
- [ ] 반대 문구 질문이 문구 민감성을 줄인다
- [ ] 함수 단위가 줄 창보다 정확하고, 그 차이가 파서 비용을 정당화한다
- [ ] 한 요청에 여러 단위를 묶어도 정확도가 크게 떨어지지 않는 지점이 있다
- [ ] git co-change 필터가 grep이 놓친 코드 밖 파일을 잡아준다
- [ ] before/after 코드 조각이 요약 문장만 넣는 것보다 낫다
- [ ] 임베딩 검색은 "고쳐야 할 코드"를 잘 못 찾는다
- [ ] 사용 케이스가 쌓일수록 recall이 실제로 오른다
- [ ] 같은 워커를 이어서 부르지 않아도 회고 품질이 비슷하다
