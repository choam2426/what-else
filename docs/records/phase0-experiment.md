## 한 줄 요약

우리가 내놓는 것은 **setup 전체**예요. 레포에 맞게 조정한 방법론과 Jev 세팅이에요. 이걸 붙였을 때 **순정 harness보다 변경 범위를 더 잘 찾고 더 효율적인지**를 확인해요. 결과가 미리 정한 기준을 넘지 못하면 setup skill을 만들지 않아요.

## 2. 비교군

| 비교군 | 내용 | 역할 |
| --- | --- | --- |
| **A. 순정 harness** | 변경 설명을 주고 "함께 고쳐야 할 곳을 모두 찾아라"만 지시해요. 에이전트는 자기 방식대로 탐색해요. | 기준 |
| **A'. 일반 방법론** | A에 [방법론](methodology.md)만 덧붙여요. 레포 맞춤도 Jev도 없어요. CLI 이름은 `A2`예요. | 방법론 자체의 효과 |
| **S−Jev. setup, Jev 없음** | setup이 이 레포에서 뽑은 규칙(관례, 형제 묶음, 경로 쌍)을 넣은 방법론이에요. Jev는 없어요. | 레포 맞춤의 효과 |
| **S. setup 전체** | S−Jev에 JevGrep CLI를 더해요. 에이전트가 찾을 대상을 직접 써서 스캔해요. | **본 비교. 진행/중단 판단에 써요** |
| C. Jev 스캔 결과만 | S에서 저장한 스캔 결과를 에이전트 검증 없이 그대로 채점해요. 추가 실행은 없어요. | 진단용 |

- 모든 비교군의 프롬프트는 **덧붙인 부분만 빼고 똑같아요.** A에게도 "빠짐없이 찾아라"를 똑같이 강하게 지시해요. 약하게 지시한 A를 이기는 건 의미가 없어요.
- **setup은 레포마다 한 번**, 가장 이른 holdout 커밋보다 앞 시점의 레포와 그때까지의 기록만 보고 해요. 규칙에 정답이 섞이지 않게 하려는 거예요.
- 케이스 스냅샷에는 git 기록이 없어요(미래 커밋이 새지 않게). 그래서 작업 중에 `git log`로 관례를 배울 수 없어요. 모든 비교군이 같은 조건이고, 기록에서 배운 것은 setup이 미리 규칙으로 넣어줘요.
- 파일럿에서는 검증 워커(설계 문서 7절 "비용 단계")를 넣지 않아요. 파일럿 결과가 좋으면 확장 단계에서 "S + 작은 모델 검증 워커"를 추가해요.
- 이전 초안의 **B**는 지금의 **S**예요.

## 3. 진행·중단 기준 (미리 정함)

파일럿 결과를 본 뒤에 기준을 바꾸면 안 돼요. 실행 전에 확정해요. 아래는 제안값이에요. 판단은 **holdout 세트**로만 해요.

**진행 조건 (둘 다 만족)**

1. **품질**: "어려운" 케이스(A가 반드시 고쳐야 할 위치를 하나 이상 놓친 케이스)의 **25% 이상**에서, A가 놓친 필수 파일을 S가 하나 이상 찾아요.
2. **비용**: S의 메인 에이전트 환산 비용과 Jev 비용을 합한 값이 A의 **1.5배 이하**예요. 품질이 같다면 S가 A보다 싸거나 빨라야 해요.

**추가로 보는 것 (진행 여부에는 쓰지 않음)**

- S가 A보다 **잃은** 필수 위치의 수. 방법론이나 JevGrep 결과에 이끌려 에이전트가 원래 찾던 곳을 놓치는지 봐요.
- C의 상위 20개 기준 recall. Jev 자체가 쓸모 있는지 봐요.
- S의 틀린 후보 수. 에이전트가 읽어야 하는 양이에요.

**중단 조건**: 진행 조건을 하나라도 못 넘으면 중단해요. 중단하면 원인을 기록하고, 설계를 바꿔 다시 시도할지 판단해요. (예: 탐색 단위나 질문 설계 문제인지, Jev 자체의 한계인지)

## 4. 데이터

### 레포 선택 기준

- 공개 레포, 활발히 개발 중, 중간 규모 (약 5만~30만 줄)
- **모델 학습 시점 이후의 커밋**이 충분히 있어야 해요. 오래된 유명 커밋은 모델이 답을 외우고 있을 수 있어요. 2026년 7월 이후 커밋을 써요.
- 파일럿은 레포 1개예요. 확장할 때는 언어가 다른 레포를 추가해요 (예: Python 백엔드 1개, TS 1개).

### 커밋 필터

- 원래 있던 파일을 **3~15개** 바꾼 커밋
- 빼는 것: 머지, 봇, revert, 포맷·lint만 바꾼 커밋, 의존성 업데이트, lock 파일만 바뀐 커밋, 이름만 바꾼 커밋
- 커밋 메시지가 변경을 설명할 수 있어야 해요 ("fix", "wip" 같은 것 제외)

### 케이스 만들기

케이스 하나는 "개발자가 핵심 변경을 방금 했고, 함께 고쳐야 할 곳을 찾는 상황"을 재현해요.

1. **스냅샷**: 부모 커밋의 파일만 뽑아서(임시 index로 `git --work-tree=… checkout`) 기록 없는 새 디렉터리를 만들고, `git init` 후 한 번 커밋해요. `.git`에 미래 커밋이 남아 있으면 에이전트가 `git log --all`로 정답을 볼 수 있어요.
2. **seed 변경**: 규칙으로 골라요. 테스트·문서가 아닌 파일 중 가장 많이 바뀐 파일의 가장 큰 hunk예요. 사람이 정답을 보고 고르지 않게 하려는 거예요.
    - seed는 **공백까지 정확한 diff**에서 가져오고, 3줄 이내로 붙은 hunk는 하나로 합쳐요. `-w` diff나 잘게 쪼갠 hunk 하나만 적용하면 들여쓰기가 바뀐 코드가 깨져요(실제로 2개 케이스가 깨져서 다시 만들었어요).
    - 만든 뒤 seed 파일이 문법적으로 맞는지 확인해요.
3. **변경 설명**: 커밋 메시지에서 **파일 경로를 지워요.** 심볼 이름은 남겨요. 실제 개발자도 자기가 바꾼 심볼은 알고 있으니까요.
4. **정답**: 커밋에서 seed hunk를 뺀 나머지 변경이에요.
    - 부모 커밋에 원래 있던 파일만 세요. 새로 만든 파일은 스캔으로 찾을 수 없어요.
    - 삭제된 파일은 원래 있던 파일이니 포함해요.
    - 공백만 바뀐 hunk(`git diff -w`로 판별), 생성 파일, lock 파일, 번역 파일, AUTHORS 같은 기여자 목록은 빼요.
    - hunk 단위 정답은 부모 커밋 기준의 줄 범위예요.
5. **분류 태그**: 정답 위치마다 종류를 붙여요. 같은 파일의 다른 곳, 호출부, 테스트·fixture, 스키마·serializer·타입 선언, 설정, 문서, migration, 그 밖의 코드 밖 파일이에요. Q4 분석에 써요.

## 5. 실행 방법

### 공통 프롬프트 (골자)

```
The following change was just made to this repository:
<변경 설명>
<seed diff>

Find every other location in this codebase that must also change for this change to be complete and consistent.
Be exhaustive. Do not modify any files.
Return the locations in the required JSON format.
```

- A'는 방법론을, S−Jev는 레포 맞춤 방법론을, S는 거기에 JevGrep 사용법(CLI 명령, 찾을 대상 쓰는 법, 출력 읽는 법)을 덧붙여요.
- 출력 형식은 JSON 스키마로 고정해요: `{ "locations": [{ "path", "start_line", "end_line", "reason" }] }`
- 방법론을 쓰는 비교군은 위치마다 `necessity`, `axis`와 축별 `coverage`를 더 받아요. 축별 보고도 방법론의 일부로 봐요. 채점은 모든 비교군을 `locations`로 똑같이 해요.

### Claude Code

```
claude -p "<프롬프트>" \
  --output-format json \
  --json-schema '<출력 스키마>' \
  --model <메인 모델> \
  --setting-sources project \
  --strict-mcp-config \
  --disable-slash-commands \
  --disallowedTools "Edit Write NotebookEdit" \
  --no-session-persistence
```

- `--bare`는 쓸 수 없어요. API 키 인증만 받아서 구독 로그인과 호환되지 않아요.
- 전역 skill과 사용자 설정을 빼서 두 비교군의 환경을 같게 해요. JevGrep도 skill이 아니라 프롬프트와 CLI로 줘요. Phase 0은 skill이 잘 트리거되는지가 아니라, Jev 스캔이 가치가 있는지를 보는 실험이에요.
- 서브에이전트(`Agent` 도구)는 두 비교군 모두 허용해요. 순정 harness의 실제 행동이니까요. 사용량은 `subagent_stats`로 기록해요.
- 권한 모드는 비대화 실행에서 막히지 않도록 정해요. 스냅샷 디렉터리 밖을 건드리지 못하게 해요.

### Codex (확장 단계)

```
codex exec "<프롬프트>" \
  --json \
  --output-schema <출력 스키마 파일> \
  -m <메인 모델> \
  --ignore-user-config \
  --ephemeral \
  -C <스냅샷 디렉터리> \
  -s <샌드박스 모드>
```

- S에서는 JevGrep이 api.typesafe.ai에 접속해야 해요. Codex 기본 샌드박스는 네트워크를 막으니 허용 설정이 필요해요.
- 토큰 사용량이 JSON 이벤트 어디에 나오는지는 실행 전에 확인해요.

### JevGrep (S 비교군용 최소 CLI)

Phase 0용으로 최소한만 만들어요. 설계 문서 13절의 "v1"보다도 작게 만들어요.

- `git ls-files` 대상, 기본 제외 경로와 비밀정보 필터 적용
- 약 60줄 줄 창(겹침 있음), 요청 하나에 단위 하나
- 입력: 에이전트가 쓴 `query.json` (변경 맥락 + 찾을 대상 T1…Tn)
- 출력: 대상별 상위 k개(파일럿 k=10), 위치·대상·점수, coverage 한 줄
- 전체 결과는 run 디렉터리에 저장 (C 비교군 채점용)

### 반복

- 케이스마다 비교군별로 **2번** 돌려요. LLM 결과는 매번 달라요.
- 확장 단계에서는 3번으로 늘려요.

## 6. 지표

| 지표 | 정의 | 출처 |
| --- | --- | --- |
| 파일 recall | 정답 파일 중 찾은 비율 (원래 있던 파일만) | 채점 스크립트 |
| hunk recall | 정답 hunk 중 찾은 비율. 후보 범위가 hunk의 부모 기준 줄 범위와 겹치면 적중 | 채점 스크립트 |
| 추가로 찾은 것 | A는 놓쳤는데 비교군이 찾은 정답 위치 수 | 채점 스크립트 |
| 잃은 것 | A는 찾았는데 비교군이 놓친 정답 위치 수 | 채점 스크립트 |
| 틀린 후보 수, precision | 정답이 아닌 후보의 수와 비율 | 채점 스크립트 |
| 메인 토큰 | 입력 + 캐시 생성 + 캐시 읽기 + 출력 | `usage` |
| 환산 비용 | 정가 기준 LLM 비용 + Jev 비용 | `total_cost_usd` (`costBasis: "list"`) + Jev `usage.input_tokens` × $0.042/M |
| 시간 | 전체 실행 시간 | `duration_ms` |
| 턴 수, 도구 호출 수 | 탐색에 들인 노력 | `num_turns`, 로그 |
| 메인 컨텍스트 최대치 | 한 번의 모델 호출에 들어간 입력 토큰의 최댓값 | `usage.iterations` |

- 구독이라 실제로 청구되지는 않아요. `total_cost_usd`는 **정가 기준 환산값**이고, 비교 용도로만 써요.
- 서브에이전트 사용량이 `total_cost_usd`와 `modelUsage`에 포함되는지는 첫 실행에서 확인해요.

## 7. 분석

- **케이스별로 짝지어 비교해요.** 같은 케이스에서 A와 각 비교군을 비교하고, 케이스별 승·무·패를 세요. 평균만 보면 쉬운 케이스 몇 개가 결과를 좌우해요.
- 어려운 케이스와 나머지를 따로 봐요. 어려운 케이스는 A가 반복 실행 중 과반에서 반드시 고쳐야 할 위치를 하나 이상 놓친 케이스예요. grep으로 찾을 수 있는지는 따지지 않아요. 문제는 에이전트가 놓치는 것이지 grep의 한계가 아니에요.
- 정답 종류(4절의 분류 태그)별로 recall을 나눠 봐요. 설계 리뷰에서 예상한 것처럼, 코드 밖 파일, fixture, 선언부 같은 한 단계 판정 종류에서 Jev가 도움이 되는지 확인해요.
- 품질과 비용을 함께 봐요. "같은 recall에 도달하는 비용"과 "같은 비용에서의 recall"이에요.
- 반복 실행 간 편차도 기록해요. 편차가 차이보다 크면 결론을 내리지 않아요.

## 8. 규모와 구독 사용량

| 단계 | 구성 | 실행 수 |
| --- | --- | --- |
| dev | Django 16개. A 1번(완료), A'·S−Jev·S로 방법론과 setup을 다듬음 | 비교군당 16 |
| holdout | pydantic 25개 + outline 25개. 방법론·setup을 확정한 뒤 A·A'·S−Jev·S를 2번씩 | 약 400 |
| 확장 | 레포 추가, 반복 3번, Codex, 검증 워커 비교군 | 수백 |

- **시범 실행으로 실행 한 번의 토큰과 시간을 먼저 재요.** 그 값으로 파일럿이 구독 한도 안에 들어오는지 계산해요.
- 구독 사용량 한도를 넘지 않도록 파일럿은 여러 번에 나눠 돌려요.
- Jev 비용은 무시할 수준이에요. 케이스 하나의 스캔이 수천 요청이어도 몇 센트 수준이에요. 병목은 요청 한도(분당 1,200회)예요.

## 14. 방향 전환: 작은 모델 + setup (2026-09-29)

dev에서 순정 Sonnet이 강했고, 어느 비교군도 편차보다 큰 차이를 내지 못했어요. "놓침을 줄인다"만으로는 가치가 약해 보여요. 그래서 핵심 질문을 바꿔요.

> **작은 모델(Haiku) + setup이 순정 큰 모델(Sonnet)만큼 변경 범위를 찾는가, 훨씬 싸게?**

- setup(규칙 뽑기)은 레포마다 한 번이라 큰 모델로 해도 돼요. 변경마다 도는 탐색만 작은 모델이 해요. 설계 문서의 "메인 → 작은 모델 워커" 구조와 같은 방향이에요.
- 놓침이 드물어도, 같은 결과를 싸게 내면 가치가 있어요.

**비교군**

| 비교군 | 모델 | 내용 |
| --- | --- | --- |
| A-Sonnet | Sonnet | 순정. **기준** (이미 있음) |
| A-Haiku | Haiku | 순정. 작은 모델이 혼자서 얼마나 떨어지는지 |
| S−Jev-Haiku | Haiku | 방법론 + 레포 규칙 |
| S-Haiku | Haiku | 방법론 + 레포 규칙 + Jev. **본 비교** |

**진행 기준 (제안, 실행 전 확정)**

1. **품질**: S-Haiku의 케이스별 평균 재현율(테스트 아닌 파일)이 A-Sonnet보다 **5%p 이상 낮지 않아요** (비열등).
2. **비용**: S-Haiku의 비용(Jev 포함)이 A-Sonnet의 **50% 이하**예요.
3. 참고: A-Haiku가 A-Sonnet보다 확실히 낮아야 이 비교가 의미 있어요. 작은 모델 혼자서도 비슷하면 setup이 할 일이 없어요.

**순서**

1. dev(Django 16개)에서 Haiku 비교군 3개를 1번씩 돌려 대략의 차이를 봐요.
2. dev-2(holdout 밖의 pydantic·outline 커밋)를 만들고 setup을 돌려요. setup의 cutoff는 holdout과 dev-2 커밋 전부보다 앞 시점이에요.
3. 차이가 보이면 비교군마다 여러 번 돌려 편차를 재고, 그다음 holdout으로 판정해요.
