# 실험 기록 색인

이 레포에서 해 본 실험을 모두 모아 둔 목록이다. 각 기록에는 무엇을 물었는지, 어떤 조건이었는지, 결과, 근거 강도가 있다. [방법 카드](../../guide/methods.md)는 이 기록들을 요약한 것이다. 카드는 판단에 필요한 조건을 스스로 담고 있어서 이 기록 없이도 읽힌다. 어느 기록이 어느 카드를 뒷받침하는지는 표의 "카드" 열에 있다.

## 한눈에 보기 (2026-10-08 기준)

**핵심 결론.** 범위 누락은 찾는 능력이 아니라 과정의 문제다. 검색 능력을 더한 도구(BM25, Jev, 탐색 워커)는 보탠 것이 거의 없었다. 효과를 낸 것은 과정 설계였다. 에이전트가 어디서 멈추고 어디서 잘못 판단하는지 관찰해서, 그 지점에 단계나 판단 기준을 넣는다. 프롬프트는 그 설계를 전달하는 수단이고, 길게 쓴 지시보다 잘못되는 지점에 놓인 짧은 지시가 효과를 냈다.

**지금의 답.** 범위 누락을 가장 많이 줄인 것은 항상 읽히는 지침에 두 단계를 넣는 것이었다.

1. **끝내기 전 확인**: 다른 구현, 같은 결정을 내리는 다른 경로, 등록 목록, 호출부, 타입과 스키마를 열어 보고 요약에 확인한 곳을 적는다.
2. **받아들이는 기준을 붙인 두 번째 검토**: 맥락 없는 서브에이전트가 요청과 diff만 보고 빠진 곳을 보고하고, 작업한 에이전트는 "그대로 두면 무엇이 깨지는지"가 코드로 확인되면 요청에 이름이 없어도 고친다.

DeepSWE 범위 실험 집합(순정이 반복해서 범위를 놓친 14과제, 14개 레포, 5개 언어)에서 과제마다 2회 돌린 범위 누락은 순정 15.5, 확인 지시만 11, 두 단계 6이었다(28건 중, R17). 지침 원문은 [방법 카드](../../guide/methods.md)에 있다.

**어떻게 여기까지 왔나.**

| 단계 | 알게 된 것 | 기록 |
| --- | --- | --- |
| Django 초기 실험 | 순정은 관례 파일(릴리스 노트, 문서)과 형제·다른 경로를 놓친다. 레포 규칙 + 확인 한 줄이 처음 보는 변경 12개에서 진짜 누락을 7 → 3으로 줄였다 | R2, R10~R11 |
| Jev와 워커 위임 | Jev는 넓은 순위 목록으로는 가장 좋았지만(상위 10에 필수 46/53), 규칙이 있으면 보태는 게 없었다. 워커 위임은 비용 3배, 시간 4~6배에 정확도는 규칙 이하 | R5~R9 |
| DeepSWE 통과율 | 테스트 통과율은 범위를 재지 못한다. 어려운 과제 18개의 실패 중 범위 누락은 3개뿐이었다. 범위 누락을 직접 판정하기로 바꿨다 | [baseline-deepswe](baseline-deepswe.md#실패-원인-분류-범위-누락인가-2026-10-02) |
| 방법 비교 | 레포 규칙, BM25 도구, 둘의 조합 모두 범위 누락을 약 40% 줄였다. 같은 판정자가 모든 방법을 함께 봐야 비교가 된다(판정자 차이가 방법 차이보다 크다) | R13 |
| 효과의 출처 | 도구도 규칙도 없는 "끝내기 전 확인" 한 단락이 같은 효과를 냈다 | R14 |
| Jev 다시 | 쓸 수 있게만 하면 1/14, 이유를 적으면 3/14과제에서 썼고, 확인 지시 대비 보탠 누락은 없었다 | R15~R16 |
| 남은 누락 | 맥락 없는 두 번째 검토가 남은 누락을 짚지만, 작업한 에이전트가 "요청에 없다"며 거절했다. 받아들이는 기준을 넣자 확인 지시 대비 절반으로 줄었다 | R17 |

**아직 모르는 것.** 관례 파일 누락(Django 같은)에서도 두 단계가 통하는지, 다른 harness와 모델에서도 그런지, 두 번째 검토의 작업당 비용, 그리고 INSTALL.md를 따라 만든 setup이 실제로 두 단계를 구축하고 검증까지 해내는지. [direction.md](../direction.md)의 할 일에 있다.
