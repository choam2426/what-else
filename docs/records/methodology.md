- 작성일: 2026-09-28
- 상태: **초안.** dev 세트(Django 16개)로만 다듬어요. holdout 세트는 이 문서를 확정한 뒤에 봐요.
- 에이전트에게 주는 실제 문구: [`bench/prompts/methodology.md`](../../bench/prompts/methodology.md) (영어)
- 관련 문서: [JevGrep 설계](jevgrep-design.md), [Phase 0 실험 설계](phase0-experiment.md)

## 한 줄 요약

에이전트가 함께 고칠 곳을 놓치는 가장 큰 이유는 **그쪽을 찾아보지 않아서**예요. 그래서 방법론의 핵심은 "어디를 봐야 하는지"를 축으로 정해주고, **축마다 무엇을 확인했는지 보고하게** 하는 거예요.

## 1. 원칙

- **관찰이 아니라 일반 원리에서 시작해요.** 축은 변경 영향 분석에서 흔히 쓰는 분류예요. dev 세트의 누락 6개는 "이 축으로 설명되는가"를 확인하는 데만 썼어요. 누락 유형을 그대로 옮기면 Django 커밋 몇 개에 맞춘 방법론이 돼요.
- **찾은 곳만이 아니라 확인한 곳을 보고해요.** "없음"도 무엇으로 확인했는지 적게 해요. 확인하지 않은 축이 드러나야 놓침이 줄어요.
- **필수와 선택을 나눠요.** "안 바꾸면 무엇이 깨지거나 틀리는가"를 한 문장으로 말할 수 없으면 선택이에요. 리팩터 범위(새 헬퍼를 기존 중복 코드에 적용 등)는 사용자 의도에 달려 있어서 기본은 선택이에요.
- **harness와 레포에 묶이지 않아요.** 특정 도구 이름이나 언어 관례를 넣지 않아요. 레포마다 다른 부분(축 E의 관례, 축 B의 형제 목록)은 setup skill이 레포에서 뽑아 설정에 저장해요.

## 2. 절차

1. **바뀐 계약을 적어요.** 이름·시그니처, 동작(반환값, 예외, 입력, 부수 효과), 데이터 형태, 지원 범위(버전, 플랫폼, 백엔드), 공개 범위(추가, deprecation, 제거).
2. **계약마다 모든 축을 확인해요.**

| 축 | 무엇을 보나 | 예 |
| --- | --- | --- |
| A. 사용처 | 바뀐 것을 참조하는 모든 곳. 동작이 바뀌면 호출부가 옛 동작에 기대는지까지 | 호출, import, 상속, override, 문자열 이름, 설정 키, 등록 |
| B. 평행 구현 | 같은 일을 해서 함께 맞춰야 하는 곳. 설명에 이름이 안 나온 형제도 | 같은 파일의 다른 부분, 백엔드별 구현, 옆에 있는 같은 역할의 명령·핸들러·컴포넌트 |
| C. 같은 판단, 다른 경로 | 같은 규칙을 다른 진입점에서 다시 적용하는 곳 | sync/async, 단건/일괄, 생성/수정, 서버/클라이언트, 검증 계층 두 곳 |
| D. 경계 | 바깥과 맞닿는 계약 | serializer, 스키마, 타입 선언, API 명세, migration, 설정 기본값, CLI 옵션, 환경 변수 |
| E. 레포 관례 | 이 레포가 이런 변경 때 함께 고치는 파일. git 기록과 기여 가이드에서 배워요 | 릴리스 노트, changelog, 레퍼런스 문서, deprecation 목록, 지원 버전 표 |
| F. 테스트 | 기대값이 바뀌는 기존 테스트. 새 테스트는 선택 | |
| G. 필요 없어진 것 (선택) | 변경으로 쓸모없어진 우회 코드, 호환 분기, 낡은 주석 | |

3. **여러 방법으로 찾아요.** 정의 이름, 속성 이름과 문자열, 에러 메시지, 버전 번호, git 기록. 한 방법으로 안 나오면 다른 방법을 써본 뒤에 "없음"이라고 해요.
4. **후보마다 검증해요.** 안 바꾸면 무엇이 깨지는지 한 문장. 못 쓰면 선택으로 내려요.
5. **끝내기 전에 축을 다시 훑어요.** 축마다 무엇을 찾아봤고 무엇이 나왔는지 적어요.

**출력**: 위치마다 `necessity`(required / optional)와 `axis`, 그리고 축별 `coverage`(찾아본 방법, 결과).

## 4. 실험에서 쓰는 방법

- **A'** (CLI에서는 `A2`): A와 같은 프롬프트에 이 방법론만 덧붙여요. Jev는 없어요. `node bench/run-agent.mts <case-dir> A2 <run-name>`
- **S−Jev**: 이 방법론에 setup이 레포에서 뽑은 규칙(5절)을 넣어요. Jev는 없어요. (아직 없음)
- **S**: S−Jev에 JevGrep CLI 사용법을 덧붙여요. 축마다 "넓게 싸게 확인하는 수단"으로 Jev를 쓸 수 있어요. 우리가 내놓는 setup 전체이고, 본 비교는 S vs A예요. (아직 없음)
- A' vs A는 일반 방법론의 효과, S−Jev vs A'는 레포 맞춤의 효과, S vs S−Jev는 Jev의 효과를 보여줘요.
- **S의 스캔은 다시 선택으로 돌렸어요** (2026-09-29). 한때 "끝내기 전에 한 번 이상"을 필수로 했는데, 작은 모델에서 스캔이 직접 탐색을 대신해 버렸어요. Jev를 붙이자 필수 파일 21개를 잃었고, 그중 13개는 스캔 결과에도 없던 곳이었어요.
- **M / M−Jev (실제 작업 흐름)**: 세션 하나 안에서 메인(Sonnet)이 작업을 받고, `change-scope-worker` 서브에이전트(Haiku)에게 브리프를 넘겨요. 브리프에는 무엇이 바뀌었는지, 이미 아는 곳, 놓치기 쉬운 곳이 들어가고, M에서는 JevGrep 질문도 들어가요. 워커는 방법론과 레포 규칙을 갖고 있어요. M에서는 받은 질문으로 먼저 스캔하고, 검증하고, 직접 탐색해서 보고해요. 메인은 보고를 검토해 최종 목록을 내요. 서브에이전트는 CLI의 `--agents`로 정의해요 (`bench/prompts/delegate.md`, `bench/prompts/worker.md`, run-agent의 `M`, `M-nojev`).
    - **메인은 레포를 읽지 않아요** (2026-09-29). 첫 스모크 테스트에서 메인이 직접 탐색해서(입력 약 68만 토큰, 18턴) 위임해도 비용이 줄지 않았고, 이미 읽은 파일 이름을 넣은 확인용 Jev 질문을 썼어요. 메인이 읽을 거면 위임할 이유가 없어요. 그래서 메인은 변경에 대해 아는 것과 레포 규칙만으로 곧바로 브리프를 쓰고, 워커 보고를 최종 목록으로 내요. 레포 규칙은 메인 프롬프트에도 넣어요(skill이 메인 컨텍스트에 로드하는 것과 같아요). Jev 질문에는 파일 이름을 쓰지 말고 "어떤 종류의 곳에 무엇을 추가·변경해야 하나"를 쓰게 해요. 아래 cascade(C)를 대신해요. C는 메인이 도구 없이 질문만 쓰고 스크립트가 이어 붙이는 방식이라 실제 흐름과 달라요.
- **cascade (C, 대체됨)**: 메인(큰 모델)이 변경·규칙·디렉터리 목록만 보고 스캔 질문을 쓰고, 스크립트가 워커 시작 전에 스캔해요. 워커(작은 모델)는 방법론 + 규칙 + "확인 안 된 후보"(대상마다 상위 3개 파일, seed 파일 제외)를 받고, 직접 스캔하지 않아요 (`bench/run-cascade.mts`, `bench/prompts/leads.md`, run-agent의 `S-leads`). 작은 모델이 쓴 질문은 "이 파일이 무슨 주제인가"처럼 이미 아는 곳을 확인하는 데 그쳤기 때문이에요.
- **JevGrep CLI** (`bench/jevgrep.mts`): 에이전트가 쓴 query를 stdin으로 받아요. 대상마다 `question`, `paths`(레포 규칙에서 고른 범위), `keywords`(범위가 예산보다 클 때 순위용)를 줘요. 한 번에 최대 1,000개 창(약 60줄), 약 1분이에요. 범위를 다 못 본 대상은 출력에 "NOT checked"로 표시해요.

## 5. 나중에 레포 맞춤이 되는 부분

setup skill이 레포를 보고 채워요.

- **축 E의 규칙**: 변경 종류마다 함께 바뀌는 파일. git co-change와 기여 가이드에서 뽑아요. 예) "새 공개 함수 → 레퍼런스 문서 + 다음 버전 릴리스 노트"
- **축 B의 형제 목록**: 같은 역할의 파일 묶음. 예) 명령 디렉터리, 백엔드 디렉터리
- **축 C의 경로 쌍**: 이 레포에서 같은 판단을 두 번 하는 곳. 예) 모델 검증과 폼 검증
- 이 지식은 `.jevgrep/config.json`과 `.jevgrep/targets/`에 쌓이고, 회고로 계속 고쳐요 ([설계](jevgrep-design.md) 9절).

**실험용 시제품** (`bench/setup.mts`)

1. **스크립트**(`bench/cochange.mts`): cutoff 이전 기록에서 co-change 요약을 만들어요. 파일 내용 없이 커밋 메타데이터만 읽어요.
    - 많은 커밋이 함께 건드리는 파일. 파일 이름의 버전 번호는 `N`으로 묶어요 (`docs/releases/6.2.txt` → `docs/releases/N.N.txt`).
    - 코드 영역마다 함께 바뀌는 영역과 파일, 비율
    - 봇 커밋, 40개 넘는 파일을 바꾼 커밋은 빼요.
2. **에이전트**: cutoff 시점 레포(기록 없음)와 co-change 요약을 보고 네 가지를 써요. 관례(E), 형제(B), 같은 판단의 여러 경로(C), 경계(D)예요. 과거 커밋을 그대로 적지 말고 일반 규칙으로 쓰게 해요.
3. **결과물**: `rules.md`. S−Jev와 S 프롬프트의 방법론 뒤에 붙어요.

## 6. 열린 질문

- **비용**: 축을 모두 확인하게 하면 턴과 토큰이 늘어요. A 대비 얼마나 느는지 A'에서 재요.
- **틀린 후보**: "빠짐없이"를 강조하면 선택·오탐이 늘 수 있어요. 필수만 채점하고 선택은 따로 세요.
- **길이**: 방법론이 길면 작은 모델이 따르기 어려워요. Haiku급에서도 따르는지 확장 단계에서 봐요.
- **dev 과적합**: dev 누락을 보고 문구를 고친 부분이 있어요(예: "설명에 이름이 안 나온 형제도"). holdout에서 A'가 A보다 나은지로만 판단해요.
